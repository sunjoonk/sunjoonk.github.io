<h2 id="beyond-upload">업로드한 파일은 어떻게 관리할까요?</h2>

비공개 프로젝트의 게시글에 계약서 한 장을 첨부한다고 가정해 보겠습니다. 파일을 S3에 올리고 주소를 DB에 저장했습니다. 화면에서 다운로드도 됩니다. 이 정도면 파일 기능이 완성된 걸까요?

프로젝트에서 탈퇴한 사람은 예전에 받은 주소로 계약서를 계속 열 수 있을까요? 업로드 도중 창을 닫으면 DB에 남은 레코드는 어떻게 될까요? 게시글을 삭제했는데 S3 삭제 요청만 실패하면 누가 다시 처리할까요?

**웹서비스의 파일 관리는 저장 위치뿐 아니라 파일의 관계, 접근 권한, 수명주기를 함께 설계하는 일**입니다. 이 글에서는 비공개 프로젝트의 첨부파일 하나를 업로드하고, 사용하고, 삭제하는 과정을 따라갑니다. 테이블과 상태 이름은 설명을 위한 설계 예시이며 서비스 요구에 맞춰 조정할 수 있습니다.

<h2 id="responsibilities">S3와 DB의 역할 나누기</h2>

S3는 계약서의 실제 바이트를 보관합니다. 관계형 DB는 그 계약서가 어느 조직에 속하는지, 누가 업로드했는지, 어떤 게시글에 첨부됐는지를 기록합니다. 애플리케이션은 요청한 사용자가 해당 게시글을 볼 수 있는지 판단하고 파일 접근을 허용합니다.

```text
사용자 ── 업로드·다운로드 요청 ──→ 애플리케이션
                                    │
                                    ├─ DB: 관계·상태 조회와 권한 판단
                                    └─ 허용된 작업의 접근 URL 발급

사용자 ── 발급된 URL로 파일 전송 ──→ 비공개 S3 버킷
```

이 구조에서는 파일 본문을 애플리케이션 서버가 매번 중계할 필요가 없습니다. 서버는 권한과 상태를 관리하고, 실제 데이터 전송은 클라이언트와 S3 사이에서 이루어집니다. 다운로드가 많다면 CloudFront를 추가해 전송과 캐시를 맡길 수 있습니다.

역할을 나눌 때는 어떤 정보의 기준을 어디에 둘지도 정해야 합니다. **서비스 안에서의 파일 관계와 사용 가능 여부는 DB를 기준으로 판단하고, 실제 객체의 존재와 저장된 크기 등은 S3에서 확인합니다.** 두 저장소가 어긋날 수 있으므로 이를 발견하고 복구하는 절차도 필요합니다.

<h2 id="metadata">DB에는 URL 대신 무엇을 저장할까요?</h2>

파일 주소 하나만 저장하면 처음에는 간단합니다. 하지만 나중에 CDN을 도입하거나 도메인을 바꾸면 저장된 주소를 수정해야 할 수 있습니다. 만료되는 사전 서명 URL을 저장했다면 그 주소는 영구적인 파일 참조로도 사용할 수 없습니다.

서비스에서는 자체 `file_id`로 파일을 식별하고, S3의 저장 위치를 별도 속성으로 보관합니다.

사용자가 올린 파일명이 `계약서.pdf`여도 객체 키는 서버가 생성합니다.

```text
tenants/{tenant_id}/files/{file_id}/{random_id}
```

원본 이름과 저장 키를 분리하면 같은 이름의 파일이 충돌하지 않고, 표시 이름을 바꿀 때 객체를 이동할 필요도 없습니다. 키에는 이름이나 이메일 같은 개인정보를 넣지 않는 편이 좋습니다. 다만 임의의 키를 사용하더라도 권한 검사는 필요합니다. 주소가 알려지면 누구나 읽을 수 있는 구조를 키의 복잡성으로 보호할 수는 없습니다.

게시글과의 관계는 `post_attachments` 같은 연결 테이블로 표현할 수 있습니다.

```text
posts ── post_attachments ── files
          post_id
          file_id
          display_order
```

외래 키와 고유 제약조건으로 잘못된 참조와 중복 첨부를 막습니다. 조직이 같은지, 해당 게시글에 첨부할 권한이 있는지는 애플리케이션이나 추가적인 DB 제약으로 검사합니다. 사용자가 제출한 `file_id`가 존재한다는 이유만으로 첨부를 허용해서는 안 됩니다.

파일 읽기 권한은 보통 게시글과 프로젝트에서 파생되도록 합니다. 프로젝트 멤버십을 파일마다 복제하면 탈퇴나 공개 범위 변경 때 서로 어긋나기 쉽습니다. 여러 게시글이 같은 파일을 공유한다면 어느 첨부 관계를 통해 접근을 허용할지도 명시해야 합니다.

S3의 메타데이터와 태그는 객체 처리나 보관 정책의 보조 정보로 활용합니다. 서비스 안에서의 파일 관계와 권한 판단의 기준은 DB에 둡니다. 또한 `ETag`가 항상 파일 전체의 MD5인 것은 아닙니다. 멀티파트 업로드나 암호화 방식에 따라 의미가 달라질 수 있으므로, 무결성 검증에는 알고리즘과 값을 명시한 체크섬을 사용합니다. [S3 객체 메타데이터](https://docs.aws.amazon.com/AmazonS3/latest/userguide/UsingMetadata.html)

<h2 id="upload-lifecycle">업로드 완료와 사용 가능 사이</h2>

사용자가 파일을 선택했다고 바로 사용 가능한 파일 레코드를 만들면, 업로드를 중단했을 때 존재하지 않는 파일이 화면에 나타날 수 있습니다. 업로드 과정을 상태별로 나누어 관리하는 편이 좋습니다.

```text
PENDING → VERIFYING → READY
              └────→ REJECTED
```

서버는 먼저 사용자의 프로젝트 권한, 허용 형식, 용량 한도와 사용량을 확인합니다. 객체 키를 생성하고 `PENDING` 레코드를 저장한 뒤, 그 키에만 업로드할 수 있는 짧은 유효기간의 사전 서명 URL을 발급합니다. 여러 파일을 동시에 업로드할 때도 사용량 한도를 지켜야 한다면 대기 중인 업로드에 대한 미리 용량을 확보하는 방식도 고려합니다.

클라이언트는 S3에 파일을 전송하고 서버에 완료를 알립니다. **완료 알림은 검증을 시작하는 신호입니다.** 서버는 DB에 기록한 위치에서 객체를 찾고 실제 크기, 필요한 체크섬과 내용을 검증합니다. 파일 형식에 따라 악성 파일 검사나 이미지 변환도 이 단계에서 수행합니다. 검증 중인 파일은 일반 다운로드 경로로 제공하지 않습니다.

`HeadObject`로 저장된 크기와 메타데이터를 확인할 수 있지만, 업로더가 지정한 `Content-Type`만으로 실제 형식을 판별할 수는 없습니다. 요청에 적힌 크기를 검사하는 것 역시 S3가 업로드 크기 제한을 강제한다는 뜻은 아닙니다. 업로드 방식에서 적용 가능한 제한과 업로드 이후 검증을 함께 설계해야 합니다.

검증을 통과하면 `READY`로 바꾸고 첨부와 다운로드를 허용합니다. 재시도된 완료 요청이 이미 삭제 중인 파일을 다시 `READY`로 돌리지 않도록, 상태 변경은 허용된 이전 상태에서만 수행합니다.

여기에는 한 가지 조건이 더 있습니다. **검증한 객체와 나중에 제공하는 객체가 같아야 합니다.** 사전 서명 URL은 기본적으로 일회용이 아니며 유효기간 동안 재사용할 수 있습니다. 같은 키의 객체를 다시 쓸 수 있다면 검증 후 내용이 바뀔 수 있습니다. [사전 서명 URL의 동작](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html)

이를 막으려면 지원되는 쓰기 작업에 `If-None-Match: *` 조건을 적용하거나, 검증한 `version_id`를 고정해 그 버전을 제공하거나, 검증한 버전을 클라이언트가 쓸 수 없는 최종 위치로 복사하는 방법을 선택할 수 있습니다. 조건부 쓰기를 사용할 때는 클라이언트가 조건을 생략한 쓰기를 할 수 없도록 서명과 정책도 맞춰야 합니다. 파일 교체에는 새 키를 발급해 이전 객체와 구분합니다. [S3 조건부 쓰기](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html)

<h2 id="authorization">AWS 권한과 사용자 권한 연결하기</h2>

권한은 두 계층으로 나누어 생각하면 이해하기 쉽습니다. IAM 역할과 버킷 정책은 서버나 작업 프로세스가 S3에서 무엇을 할 수 있는지 정합니다. 서비스의 권한 로직은 지금 로그인한 사용자가 이 계약서를 읽을 수 있는지 판단합니다.

서버에 `GetObject` 권한이 있다는 사실은 모든 로그인 사용자에게 모든 파일의 다운로드 URL을 발급해도 된다는 뜻이 아닙니다. 다음과 같은 요청 흐름이 필요합니다.

```text
GET /posts/{post_id}/attachments/{file_id}/download

1. 사용자 인증
2. 조직·프로젝트·게시글 접근 권한 확인
3. 해당 게시글과 파일의 첨부 관계 확인
4. 파일이 READY이고 차단·삭제되지 않았는지 확인
5. DB에서 조회한 객체 위치로 다운로드 URL 발급
```

클라이언트가 보낸 `bucket`과 `object_key`를 그대로 서명하는 API는 피합니다. 서비스 식별자로 요청을 받고, 접근 가능한 파일의 위치를 서버가 조회해야 합니다.

비공개 파일 저장소에서는 Block Public Access를 유지하고, ACL을 비활성화하는 `Bucket owner enforced` 설정을 사용하는 구성을 기본으로 삼습니다. AWS는 새 버킷에 이 설정들을 기본 적용합니다. 기존 버킷은 실제 설정을 확인해야 합니다. [S3 접근 설정](https://docs.aws.amazon.com/AmazonS3/latest/userguide/granting-public-access.html)

서버 역할은 필요한 버킷·접두사·작업으로 범위를 제한합니다. 업로드 URL을 발급하는 역할에 전체 버킷 삭제 권한까지 줄 필요는 없습니다. 브라우저에 장기 AWS 자격 증명을 전달하지 않고, 서버는 실행 환경에서 제공하는 역할을 사용합니다.

CORS는 브라우저가 다른 출처의 리소스와 통신하는 규칙입니다. 사용자 인증이나 객체 권한을 대신하지 않습니다. 허용된 웹사이트에서 요청했다는 사실만으로 계약서에 접근할 자격이 생기지 않습니다.

<h2 id="delivery">다운로드 URL과 캐시의 권한</h2>

사전 서명 URL은 해당 주소를 가진 사람이 정해진 작업을 수행할 수 있는 임시 접근 수단입니다. 필요한 시간만 유효하게 발급하고, 전체 URL이 분석 도구나 로그에 불필요하게 남지 않도록 합니다. DB에는 URL 자체를 저장하지 않고, 권한 검사 후 필요할 때 생성합니다.

프로젝트에서 사용자를 제외해도 이미 발급한 S3 URL은 DB의 멤버십 변경을 직접 알지 못합니다. 별도 차단 조치가 없다면 유효기간 동안 계속 사용할 수 있습니다. 유효기간은 지정된 만료 시간뿐 아니라 서명에 사용한 임시 자격 증명의 만료에도 영향을 받습니다. [사전 서명 URL의 만료와 제한](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html)

따라서 짧은 만료 시간은 권한 회수 지연을 줄이는 수단입니다. 매 요청마다 현재 권한을 확인해야 한다면 인증 프록시처럼 요청 경로에서 권한을 다시 판단하는 구조를 검토합니다. 이미 내려받은 파일까지 회수할 수 있는 것은 아닙니다.

CloudFront를 사용한다면 원본 접근과 사용자 접근을 구분해야 합니다. OAC는 CloudFront가 비공개 S3 원본을 읽을 수 있도록 제어합니다. 사용자에게 비공개 파일을 제공하려면 애플리케이션에서 권한을 확인하고 CloudFront 서명 URL이나 서명 쿠키를 발급하는 구성이 별도로 필요합니다. [CloudFront 비공개 콘텐츠 접근 제어](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-overview.html)

공개 이미지와 비공개 계약서는 경로와 캐시 정책을 명확히 구분합니다. 공개 캐시에 들어간 파일은 DB의 공개 여부를 바꾸거나 원본을 삭제하는 것만으로 즉시 사라지지 않습니다. 사용자 업로드 파일을 별도 출처에서 제공하고, HTML이나 SVG처럼 실행 가능한 내용을 포함할 수 있는 형식의 허용·다운로드 정책도 정합니다.

<h2 id="failure-and-deletion">부분 실패와 삭제를 복구하는 방법</h2>

S3 저장과 관계형 DB 갱신은 하나의 DB 트랜잭션으로 묶이지 않습니다. S3 업로드가 성공한 뒤 DB 갱신이 실패할 수 있고, DB 레코드를 만든 뒤 업로드가 시작되지 않을 수도 있습니다.

S3는 객체 쓰기 이후 읽기와 목록 조회에 강한 일관성을 제공합니다. 그러나 이것이 외부 DB와의 원자적 처리를 보장하지는 않습니다. 이 문제는 애플리케이션이 상태와 재시도를 통해 해결해야 합니다. [S3의 일관성](https://aws.amazon.com/s3/consistency/)

  <table>

파일 삭제는 먼저 DB 트랜잭션에서 `DELETING`으로 바꾸고 삭제 작업을 기록하는 방식으로 설계할 수 있습니다. 애플리케이션은 신규 다운로드 URL 발급을 중단하고, 백그라운드 작업이 S3 객체를 지웁니다. 성공하면 `DELETED`로 변경합니다.

```text
DB 트랜잭션: DELETING 변경 + 삭제 작업 기록
                         ↓
백그라운드 작업: S3 삭제 → 성공 시 DELETED
                    └── 실패 시 재시도
```

삭제 작업을 같은 DB의 outbox 테이블에 기록하면 상태만 바뀌고 큐 전송이 실패해 작업이 사라지는 문제를 줄일 수 있습니다. 백그라운드 작업 프로세스는 outbox의 기록을 읽고 삭제를 수행한 뒤 결과를 남깁니다. 중복 실행되더라도 이미 삭제된 객체를 다시 삭제하는 경우도 삭제가 완료된 것으로 처리하도록 만듭니다.

여러 게시글이 같은 파일을 참조한다면 첨부 관계 제거와 객체 삭제는 별개입니다. 남은 참조와 보존 정책을 확인하고, 삭제 중인 파일에 새 참조가 추가되지 않도록 동시성도 제어해야 합니다.

버전 관리를 사용하는 버킷에서는 삭제 마커를 만드는 일반 삭제와 과거 버전의 영구 삭제도 구분해야 합니다. 완전히 삭제해야 한다면 이전 버전과 썸네일 같은 파생 파일, 복제본까지 삭제 범위에 포함합니다. 보존 요구에 따라 삭제 시점과 정책은 달라질 수 있습니다.

<h2 id="operations">시간이 지나도 관리 가능한 구조</h2>

정상 요청만 처리하면 시간이 지나면서 미완성 업로드와 고아 객체가 쌓입니다. 주기적인 점검에서는 오래된 `PENDING`, DB가 참조하지 않는 객체, `READY`인데 실제 객체가 없는 파일을 찾아야 합니다.

고아 객체는 발견 즉시 지우지 않습니다. 진행 중인 업로드나 처리가 지연된 작업일 수 있습니다. 업로드 세션과 생성 시각을 확인하고 유예 기간을 둔 뒤 정리합니다. 아직 유효한 업로드 URL로 객체가 다시 생성될 가능성도 고려해야 합니다.

S3 이벤트로 검증이나 변환을 시작할 때도 중복과 순서 역전을 예상합니다. 이벤트 알림은 최소 한 번 전달되도록 설계되어 있으며 발생 순서대로 도착하는 것은 보장되지 않습니다. 같은 작업을 여러 번 처리해도 결과가 달라지지 않게 만들고, 오래된 이벤트가 삭제된 파일을 되살리지 못하도록 상태 전이를 제한합니다. [S3 이벤트 전달 특성](https://docs.aws.amazon.com/AmazonS3/latest/userguide/notification-how-to-event-types-and-destinations.html)

운영 지표에는 저장 용량뿐 아니라 다운로드 트래픽, 실패한 검증·변환·삭제 작업, 오래 대기하는 업로드를 포함합니다. 미완료 멀티파트 업로드와 불필요한 과거 버전도 정리 대상입니다. Lifecycle 규칙을 사용할 때는 DB에서 아직 사용하는 객체가 S3에서 먼저 만료되지 않도록 보존 정책을 맞춥니다.

처음의 계약서로 돌아가 보겠습니다. 계약서의 소속은 DB의 관계로 설명할 수 있어야 합니다. 다운로드 허용 여부는 현재 사용자의 권한과 파일 상태로 판단해야 합니다. 업로드나 삭제가 중간에 끊겼다면 어느 상태에서 다시 시작할지도 정해져 있어야 합니다.

**파일을 저장한 다음 어떤 일이 일어날지까지 정할 때, 업로드 기능은 운영할 수 있는 파일 관리 기능이 됩니다.**
