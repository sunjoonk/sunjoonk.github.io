<h2 id="starting-point">Astra를 바라보는 출발점</h2>

AI의 발전을 이야기할 때 우리는 먼저 정답률을 묻는다. 어려운 수학 문제를 얼마나 잘 푸는지, 코드를 얼마나 정확하게 작성하는지. 그런데 실제로 일을 맡기는 입장에서 더 궁금한 질문은 따로 있다. **“중간에 길을 잃지 않고, 내가 원했던 결과까지 도달할 수 있을까?”**

GPT-6 Astra를 살펴보며 주목한 지점도 여기에 있다. OpenAI는 이 모델을 컴퓨터 사용, 브라우징, 소프트웨어 개발, 과학과 전문 업무에 걸친 고성능 모델로 소개한다. 특히 여러 단계로 이루어진 작업을 코드·브라우저·업무 소프트웨어에 걸쳐 수행하는 능력을 강조한다. 이것은 제작사의 설명이며, 독립적인 검증 결과와는 구분해야 한다. [모델 가이드](https://developers.openai.com/api/docs/guides/latest-model)

이 글에서 다루는 대상은 OpenAI의 **GPT-6 Astra**다. ChatGPT라는 서비스의 모든 기능을 이 모델 자체의 능력으로 환산하지는 않는다. 예를 들어 공식 API 사양상 Astra는 텍스트와 이미지를 입력받고 텍스트를 출력한다. 음성·영상 입력은 해당 모델에 지원되는 것으로 표기되어 있지 않다. 이미지 생성 도구를 호출할 수 있다는 사실과 모델이 이미지를 직접 출력한다는 말도 다르다. [Astra 모델 사양](https://developers.openai.com/api/docs/models/gpt-6-astra)

‘범용 AGI’라는 표현을 결론으로 놓고 시작하기보다, 어떤 변화가 그런 기대를 설명할 수 있는지부터 살펴보려 한다.

위 수치는 [공식 모델 비교 페이지](https://developers.openai.com/api/docs/models/compare)의 기본 토큰 단가다. Astra는 입력이 272,000토큰을 넘는 요청에 별도 배수가 적용되며, 도구 사용료도 구분해야 한다. [Astra 가격 조건](https://developers.openai.com/api/docs/models/gpt-6-astra)

두 모델의 컨텍스트 크기와 최대 출력은 같다. 따라서 Astra의 차이를 “더 많은 내용을 한 번에 넣을 수 있다”로 설명하기는 어렵다. **담을 수 있는 정보의 양과 그 정보를 끝까지 활용하는 능력은 별개의 문제**다. 컨텍스트 길이는 용량을 말해줄 뿐, 긴 작업에서의 판단 품질을 보증하지 않는다.

컴퓨터 사용, 구조화된 출력, 여러 에이전트의 작업 조율 같은 기능도 GPT-5.6에 이미 있었다. OpenAI는 Astra가 긴 작업의 일관성과 지시 이행에서 개선되었다고 설명한다. 새로 눈여겨볼 것은 기존 도구를 활용하는 흐름과 그 흐름에 사람이 개입하는 방식이다. [이전 세대와의 차이](https://developers.openai.com/api/docs/guides/latest-model)

<h2 id="workflow">작업을 이어가는 세 가지 변화</h2>

<h3>01. 도구를 기다리는 동안에도 이어지는 작업</h3>

비동기 도구 호출은 외부 도구가 실행되는 동안 모델이 추론이나 다른 독립적인 작업을 계속할 수 있게 한다. 도구의 실제 실행과 대기 중인 결과 관리는 애플리케이션이 담당한다. 모델이 혼자 모든 실행 환경을 운영하는 것은 아니다. [Async tool calling](https://developers.openai.com/api/docs/guides/async-tool-calling)

이를 블로그 조사에 적용해 상상해보자. 자료를 불러오는 동안 이미 확보한 문서를 비교하고 글의 구조를 잡을 수 있다. 다만 아직 받지 못한 자료의 결론을 미리 써서는 안 된다. 내가 보는 가치는 단순한 동시 실행보다 **무엇을 먼저 해도 되고, 무엇은 기다려야 하는지 판단하는 작업 설계**에 있다. 이는 기능의 활용 가능성에 대한 해석이며 실제 속도 측정 결과는 아니다.

<h3>02. 끝날 때까지 기다리지 않아도 되는 수정</h3>

Mid-turn steering은 모델이 작업하는 도중 새로운 사용자 지시를 전달하는 기능이다. Responses API의 WebSocket 연결에서 완료된 작업을 유지하면서 수정 사항을 이어지는 처리에 반영하도록 설계되어 있다. [Mid-turn steering](https://developers.openai.com/api/docs/guides/steering)

가령 보고서를 작성하는 도중 “가격 분석보다 실패 사례에 비중을 더 두자”고 방향을 바꿀 수 있다. 내게는 이것이 협업의 질과 연결되는 변화로 보인다. 요구사항은 시작할 때 완성되지 않는다. 작업하면서 목적을 더 정확히 이해하고, 이미 만든 결과를 남긴 채 방향을 고치는 일이 자연스럽게 일어나기 때문이다.

<h3>03. 필요한 순간에 조절하는 추론</h3>

대화 중 추론 수준을 바꾸면서 기존 프롬프트의 캐시를 유지하는 기능도 추가되었다. 어려운 단계에서 추론을 높이고 일상적인 후속 작업에서 낮추는 구성이 가능하다. [추론 설정 변경 안내](https://developers.openai.com/api/docs/guides/latest-model#whats-new)

이 세 기능을 종합하면, 내 해석에서 Astra의 방향은 더 큰 작업 단위를 다룰 수 있는 협업에 가깝다. 다만 API 기능의 존재만으로 실제 완수율이 높아졌다고 입증할 수는 없다. 실행 환경이 그 기능을 제대로 연결했는지, 모델이 각 기능을 적절한 순간에 사용하는지까지 평가해야 한다.

<h2 id="evaluation">높은 평가를 읽는 방법</h2>

OpenAI는 일부 평가에서 Astra가 더 적은 출력 토큰으로 더 나은 결과를 내고, 높은 토큰 단가에도 불구하고 작업당 추정 API 비용은 낮아졌다고 설명한다. 이 주장은 모든 작업에서 비용이 줄어든다는 의미가 아니다. [공식 성능 설명](https://developers.openai.com/api/docs/guides/latest-model)

가격표를 기준으로 단순화하면 입력·출력 단가가 각각 Sol의 2.5배다. 입력과 캐시, 도구 비용을 제외하고 출력 비용만 비교할 때, Astra의 출력량이 Sol의 40%이면 비용이 같아진다. 예를 들어 Sol이 10,000토큰을 출력하면 $0.20이고, Astra는 4,000토큰에 $0.20이다. **단가가 높은 모델도 필요한 토큰이 충분히 줄면 경제적일 수 있다.** 다만 이 계산은 손익분기 예시이며 실제 성능을 측정한 결과가 아니다.

성능을 볼 때도 같은 구분이 필요하다. ‘최고 수준’이라는 제작사의 설명, 잘 나온 데모, 동일한 조건에서 반복한 평가는 서로 다른 증거다. 이번에 확인한 개발자 문서만으로는 독립 평가의 구체적인 점수와 재현 조건, AGI에 대한 평가자들의 합의까지 확정할 수 없었다. 그래서 확인하지 못한 벤치마크 수치를 채워 넣지 않았다.

내가 직접 비교한다면 다음 기준으로 실험을 설계하고 싶다.

- **완수율:** 결과물이 실제로 실행되고, 처음에 정한 요구사항을 만족하는가.
- **개입 횟수:** 사람이 방향을 바로잡거나 누락을 지적해야 하는 횟수는 얼마나 되는가.
- **복구 능력:** 잘못된 도구 결과나 테스트 실패 뒤에 원인을 찾아 다시 진행하는가.
- **전체 비용:** 입력·출력·도구 호출·재시도에 든 비용과 시간을 합치면 어떠한가.

같은 저장소, 같은 과제, 같은 도구 권한을 주고 여러 번 실행해야 한다. 실패한 실행도 포함해야 한다. 이런 조건을 갖춰야 “놀라운 결과 하나”를 넘어 “맡길 수 있는 일의 범위가 넓어졌다”는 판단에 가까워질 수 있다. 위 항목은 앞으로 확인하고 싶은 평가 기준이다.

<h2 id="agi">그래서, AGI일까?</h2>

이 글에서는 AGI를, 서로 다른 분야의 새로운 문제에도 능력을 옮겨 적용하고 적은 개입으로 안정적인 결과를 내는 범용 지능이라는 작업상의 기준으로 생각해본다. 이는 공식 인증 기준을 인용한 정의가 아니라, Astra를 평가하기 위해 내가 세운 질문이다.

이 관점에서 범용성에 대한 기대는 이해할 만하다. 코드 작성, 정보 조사, 문서 작성이 하나의 목표 아래 연결된다면 사람이 맡길 수 있는 일의 단위가 달라지기 때문이다. “이 함수 작성해줘”에서 “이 문제를 조사하고 해결안을 구현한 다음 검증해줘”로 요청이 바뀌는 것이다. **AGI를 떠올리게 하는 요인을 꼽자면, 나는 이 작업 범위의 확장을 들겠다.**

하지만 그것만으로 AGI가 입증되지는 않는다. 익숙하지 않은 환경으로 능력이 옮겨가는지, 장기간 작업에서 실수가 쌓이지 않는지, 잘못된 전제를 알아차리는지, 사람의 의도를 정확하게 좁혀가는지는 따로 확인해야 한다. 훌륭한 도구 사용과 모든 분야에서의 안정적인 일반화 사이에는 여전히 검증할 질문이 많다.

공식 가이드에도 마찰이 남아 있다. Astra는 확인 질문 때문에 예상보다 일찍 멈출 수 있고, 작은 코드 변경에도 검증 범위를 넓힐 수 있다고 안내한다. 높은 능력과 적절한 자율성은 같은 말이 아니다. [행동 특성과 한계](https://developers.openai.com/api/docs/guides/latest-model#prompting-best-practices)

따라서 현재 자료로 내릴 수 있는 내 판단은 이렇다. Astra는 범용적인 업무 수행을 살펴볼 만한 중요한 모델이지만, ‘AGI 달성’이라는 확정적인 결론은 이 글의 근거를 넘어선다.

<h2 id="reflection">개발자로서의 감상</h2>

<blockquote>
  <p>내가 기대하는 변화는 AI가 한 번에 얼마나 멋진 답을 내는지보다, 사람이 얼마나 적게 되짚어주어도 일을 끝낼 수 있는지에 있다.</p>
</blockquote>

자료를 읽으며 가장 흥미로웠던 부분은 새로운 기능의 수보다 협업의 형태였다. 도구를 기다리면서 가능한 일을 하고, 진행 중인 요구사항 변경을 받아들이고, 필요한 단계에 더 많은 추론을 쓰는 방식은 실제 업무의 리듬과 닮아 있다.

이 방향이 실무에서 반복해서 확인된다면 개발자의 역할도 조금 달라질 것 같다. 모든 구현 단계를 설명하기보다 목표와 제약을 명확하게 만들고, 결과가 맞는지 판단할 근거를 준비하는 일이 더 중요해질 것이다. 테스트, 좋은 예제, 정리된 요구사항은 그런 협업의 공통 언어가 될 수 있다.

동시에 나는 ‘스스로 잘한다’는 인상만으로 검토를 생략하고 싶지는 않다. 긴 작업에서 중요한 것은 마지막 문장의 자신감이 아니라 중간 선택들이 남긴 근거다. 어디까지 확인했고 무엇을 가정했는지 드러나는 결과물이 더 오래 신뢰를 얻을 것 같다.

아직 직접 비교 실험을 해보지 않은 지금의 감상은 기대와 유보가 함께 있다. AGI라는 이름을 먼저 붙이기보다, 내가 실제로 겪는 복잡한 작업 하나를 얼마나 잘 완수하는지 보고 싶다. Astra를 이해하는 다음 단계도 그 작은 검증에서 시작하려 한다.
