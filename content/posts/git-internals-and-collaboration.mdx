<h2 id="question">파일은 8000인데 커밋에는 5000</h2>

요청 제한 시간을 바꾸고 있다. 원래 값은 3000. 먼저 5000으로 고쳐 `git add config.txt`를 실행했다. 다시 생각해보니 더 기다려도 될 것 같아 파일을 8000으로 수정했다. 그리고 커밋했다.

```text
3000 ── 파일 수정 ──→ 5000 ── git add ──→ 파일을 8000으로 수정 ── git commit
```

커밋에 남는 값은 **5000**이다. `add`는 “이 파일의 앞으로 생길 수정까지 포함하라”는 예약이 아니다. 실행한 시점의 내용을 다음 커밋에 쓸 상태로 준비한다. 이후 편집은 다시 반영해야 한다. [git-add](https://git-scm.com/docs/git-add)

이 차이를 이해하려면 파일 이름 하나보다, 그 파일을 바라보는 세 위치가 필요하다. **작업 트리**는 지금 편집하는 파일, **인덱스**는 다음 커밋에 담을 상태, **HEAD**는 현재 커밋을 가리킨다. 이 글의 예제는 이미 커밋된 파일 하나를 수정하고, `-a`나 경로 지정 없이 커밋하는 경우다.

<h2 id="staging">같은 파일의 세 값을 움직여보기</h2>

아래는 5000을 `add`한 다음, 파일만 8000으로 다시 고친 순간이다. 먼저 **git commit**을 눌러보자. 그다음 **처음 사례로** 돌아와 **git add config.txt → git commit** 순서로 눌러보자. 어느 위치의 값이 다른 위치로 전달되는지 보면 된다.

<GitSnapshot />

첫 번째 경우에는 HEAD만 5000이 되고, 작업 파일의 8000은 남는다. 두 번째 경우에는 인덱스를 먼저 8000으로 갱신했으므로 새 커밋에도 8000이 들어간다. 커밋을 했다고 작업 중이던 모든 수정이 사라지거나 기록되는 것은 아니다.

평소 `git commit -a`를 쓴다면 결과가 다르게 느껴질 수 있다. 그 옵션은 추적 중인 파일의 수정·삭제를 자동으로 스테이징한 뒤 커밋한다. 새 미추적 파일까지 포함하지는 않는다. 여기서는 기본 동작을 보기 위해 그 편의를 제외했다. [git-commit](https://git-scm.com/docs/git-commit)

<h2 id="diff">두 diff가 서로 다른 이유</h2>

처음 사례에는 서로 다른 변경이 두 개 있다. 3000에서 5000으로 바꾼 내용은 이미 준비됐고, 5000에서 8000으로 바꾼 내용은 아직 준비되지 않았다. 비교할 두 끝점을 정하면 명령어가 읽힌다.

```text
git diff          인덱스 5000 → 작업 파일 8000
git diff --staged  HEAD  3000 → 인덱스   5000
```

`git diff`는 아직 스테이징하지 않은 변경을, `git diff --staged`는 현재 커밋에 비해 준비한 변경을 보여준다. 다시 `add`하면 첫 번째 diff는 비지만, 두 번째에는 3000에서 8000으로 바뀌는 내용이 남는다. **diff가 비었다는 말에는 무엇과 비교했는지가 필요하다.** [git-diff](https://git-scm.com/docs/git-diff)

`git status --short`의 두 칸도 같은 구분을 한다. 이 예제의 `MM config.txt`는 스테이징된 수정과 그 뒤의 미스테이징 수정이 모두 있다는 뜻이다. 앞의 `M`은 인덱스, 뒤의 `M`은 작업 트리 쪽 변경이다. 커밋 직후에는 앞 칸이 공백이 된다. [짧은 상태 표시](https://git-scm.com/docs/git-status#_short_format)

실제 저장소에서도 다음 세 명령을 함께 보면 된다. 새 미추적 파일은 일반 `git diff`에 나오지 않으므로 상태 목록을 먼저 읽는다.

```bash
git status --short
git diff -- config.txt
git diff --staged -- config.txt
```

<h2 id="objects">커밋 안에서는 어디에 남을까?</h2>

여기까지는 세 위치의 값만 봤다. 이제 인덱스의 5000을 커밋하면 무엇이 생기는지 한 단계만 내려가 보자.

```text
HEAD → main → 새 commit
                ├─ parent → 이전 commit
                └─ tree
                    └─ config.txt → blob: "timeout = 5000"

작업 파일: "timeout = 8000"   ← 이번 커밋에 담기지 않은 편집
```

**blob**은 파일 내용, **tree**는 이름과 내용 객체의 연결을 담는다. **commit**은 루트 tree와 부모 커밋, 작성 정보와 메시지 등을 연결한다. 보통 HEAD가 현재 브랜치를 가리키고, 커밋을 만들면 그 브랜치가 새 커밋으로 전진한다. [객체 구조](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects), [참조와 HEAD](https://git-scm.com/book/en/v2/Git-Internals-Git-References)

커밋에서 tree를 따라가면 그 시점의 파일 상태를 읽을 수 있다. 변경하지 않은 내용은 기존 객체를 재사용한다. 브랜치도 이 스냅샷을 가리키는 이름이므로, 브랜치를 만든다고 프로젝트 파일 전체를 새로 복사할 필요가 없다.

예제의 `config.txt`가 커밋된 저장소에서 아래 명령은 내용을 읽기만 한다. 첫 줄은 커밋이 가리키는 구조를, 나머지 두 줄은 같은 파일의 커밋 버전과 인덱스 버전을 보여준다.

```bash
git cat-file -p HEAD
git show HEAD:config.txt
git show :config.txt
```

이름이 같아도 읽는 위치가 다르면 내용이 다를 수 있다. 인덱스는 파일 이름만 모아둔 목록이 아니라, 다음 스냅샷을 구성하는 내용의 참조를 가지고 있다.

<h2 id="practice">다음 커밋 전에 확인할 것</h2>

내가 이 구분을 실무에서 쓰는 순간은 커밋 직전이다. “파일을 다 고쳤나?”에 이어 “그중 무엇을 이번 기록에 넣었나?”를 묻는다.

```bash
git status --short
git diff --staged
# 준비된 변경이 이번 커밋의 의도와 맞는지 읽는다.
git commit -m "Increase request timeout"
git status --short
```

여러 수정 중 일부만 기록하고 싶다면 `git add -p`로 변경 덩어리를 고를 수 있다. 이때 작업 파일을 테스트한 결과가 부분 스테이징된 커밋의 동작까지 보증하지는 않는다. 두 상태가 다르기 때문이다. 커밋할 상태에서도 관련 동작이 성립하는지 확인해야 한다.

좋은 커밋을 남기는 첫 습관은 명령어를 더 외우는 것보다 작다. **편집한 것, 준비한 것, 기록한 것을 구분해서 읽는 일.** 다음번 `git diff`가 비어 있을 때도, 이제 어디를 비교했는지부터 떠올릴 수 있다.

2026년 10월 17일 Git 공식 문서를 확인했다. 화면의 사례는 파일 하나에 대한 설명용 모델이다. 충돌 중 인덱스, 부분 스테이징의 구현, 병합과 복구는 이 글의 범위에서 제외했다.

- [git-add](https://git-scm.com/docs/git-add): 실행 시점의 내용을 인덱스에 반영하는 동작.
- [git-commit](https://git-scm.com/docs/git-commit): 기본 커밋과 `-a` 옵션의 차이.
- [git-diff](https://git-scm.com/docs/git-diff), [git-status](https://git-scm.com/docs/git-status): 비교 대상과 상태 표시.
- [Git Objects](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects), [Git References](https://git-scm.com/book/en/v2/Git-Internals-Git-References): 스냅샷과 이름의 연결.
