<h2 id="question">익숙한 명령어에서 시작하는 질문</h2>

코드를 고치고, `git add`를 하고, 커밋을 남긴다. 동료의 변경을 가져와 합치고, 충돌이 나면 잠시 손을 멈춘다. Git은 개발하는 하루에 자연스럽게 끼어 있다. 그런데 익숙하게 사용한다는 것과 그 동작을 설명할 수 있다는 것은 조금 다른 일이다.

커밋은 수정한 줄을 어디에 저장할까? 큰 프로젝트에서도 브랜치는 왜 금방 만들어질까? 파일 내용이 같아 보이는데 rebase를 하면 왜 커밋 해시가 달라질까?

이번에는 명령어를 외우는 자리에서 한 걸음 들어가 보고 싶다. **무엇을 저장하고, 어떤 이름을 움직이며, 서로 다른 변경을 어떻게 합치는지** 이해하면, 평소 쓰는 명령어들도 하나의 구조로 연결된다.

이 글의 명령어는 사용량 통계에 따른 순위가 아니라 일반적인 개발 흐름을 기준으로 골랐다. 예제는 기본 브랜치가 `main`, 원격 이름이 `origin`인 저장소를 가정한다. 협업 방식에 대한 제안은 이 원리를 바탕으로 한 필자의 판단이다.

<h2 id="objects">Git은 무엇을 저장할까?</h2>

Git의 중심에는 **내용으로 주소를 정하는 객체 저장소**가 있다. 객체의 종류·길이로 만든 헤더와 내용 바이트를 해시해 ID를 얻고, 그 ID로 객체를 다시 찾는다. 같은 객체를 매번 새로 복사할 필요가 없다.

주요 객체는 네 가지다.

- **blob:** 파일의 내용. 파일 이름은 포함하지 않는다.
- **tree:** 이름과 파일 모드, blob 또는 하위 tree의 ID를 연결하는 디렉터리 구조.
- **commit:** 루트 tree, 부모 커밋, 작성자·커미터 정보와 메시지.
- **tag:** 주석 태그의 대상 객체와 태그 작성자, 메시지 등을 담는 객체.

커밋의 tree를 따라가면 그 시점에 기록한 파일 전체의 상태, 즉 스냅샷을 얻는다. 변경하지 않은 파일과 디렉터리는 기존 객체를 재사용한다. 첫 커밋에는 부모가 없고, 보통의 커밋에는 하나, 두 갈래를 합친 merge commit에는 둘이 있다. 이 부모 관계가 커밋의 방향성 비순환 그래프, DAG를 만든다. [Git Objects](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects), [Git References](https://git-scm.com/book/en/v2/Git-Internals-Git-References)

```text
commit ──→ root tree ──→ README.md의 blob
  │             └────→ src tree ──→ app.js의 blob
  └─────→ parent commit
```

직접 들여다보는 것도 어렵지 않다. 커밋이 있는 저장소에서 다음 명령은 객체를 읽기만 한다.

```bash
git cat-file -p HEAD
git cat-file -p 'HEAD^{tree}'
git ls-tree -r HEAD
```

첫 결과에서 `tree`, `parent`, `author`, `committer`를 찾을 수 있다. 커밋 ID는 파일 내용만의 해시가 아니므로, 부모나 메시지 등 커밋 내용이 바뀌면 ID도 달라진다. 이것이 이력 재작성에서 새 커밋이 생기는 이유다. [객체 구성](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects)

전통적인 SHA-1 저장소에서는 ID가 40자리 16진수다. Git에는 SHA-256 객체 형식도 있으므로 모든 저장소의 ID 길이를 40자리로 가정해서는 안 된다. 여기서 해시는 내용을 식별하는 수단이며 작성자 신원을 증명하는 서명과는 구분된다. [해시 전환 문서](https://git-scm.com/docs/hash-function-transition)

그렇다면 파일 한 줄을 고칠 때마다 전체 내용을 계속 저장하니 비효율적이지 않을까? Git은 저장 공간도 따로 최적화한다. 개별 loose object는 압축해서 보관하고, 객체들을 packfile에 모을 때는 비슷한 객체 사이의 차이를 델타로 저장할 수 있다. **논리적으로는 스냅샷을 다루고, 물리적으로는 압축과 델타를 활용한다.** 화면에 보이는 diff와 저장 형식은 같은 개념이 아니다. [Packfiles](https://git-scm.com/book/en/v2/Git-Internals-Packfiles)

<h2 id="staging">add와 commit 사이</h2>

작업할 때는 세 상태를 구분하면 편하다. 에디터에서 수정하는 **작업 트리**, 다음 커밋에 담을 상태를 준비하는 **인덱스**, 현재 커밋인 **HEAD**다. 인덱스를 보통 스테이징 영역이라고 부른다.

`git add`는 파일 이름을 예약하는 명령이 아니다. 실행한 시점의 내용을 인덱스에 반영한다. 이후 같은 파일을 다시 수정하면 그 수정은 자동으로 스테이징되지 않는다. `git add -p`로 일부 변경만 고를 수도 있다. [git-add](https://git-scm.com/docs/git-add)

```text
작업 트리 ── git add ──→ 인덱스 ── git commit ──→ 새 커밋

git diff          : 인덱스 ↔ 작업 트리
git diff --staged : HEAD ↔ 인덱스
```

기본적인 `git commit`은 인덱스에 준비한 상태로 커밋을 만들고 현재 브랜치를 전진시킨다. 그래서 커밋 직전에 확인해야 할 것은 `git diff --staged`다. 일반 `git diff`가 비어 있어도 스테이징된 변경은 남아 있을 수 있다. 새로 만든 미추적 파일도 일반 diff에는 나오지 않으므로 `git status`를 함께 본다. [git-commit](https://git-scm.com/docs/git-commit), [git-diff](https://git-scm.com/docs/git-diff), [git-status](https://git-scm.com/docs/git-status)

이 구분은 커밋의 품질과 연결된다. 로그인 오류를 고치다가 발견한 이름 변경을 함께 넣기보다, `add -p`로 나누면 각 커밋의 이유가 분명해진다. 나중에 동료가 읽거나 되돌릴 때도 판단할 범위가 작아진다.

상태와 비교는 [status](https://git-scm.com/docs/git-status)·[diff](https://git-scm.com/docs/git-diff), 기록은 [add](https://git-scm.com/docs/git-add)·[commit](https://git-scm.com/docs/git-commit), 공유는 [fetch](https://git-scm.com/docs/git-fetch)·[push](https://git-scm.com/docs/git-push)를 기준으로 정리했다.

특히 `fetch`와 `pull`은 구분해서 이해할 만하다. `fetch`는 원격 객체와 참조를 가져온다. 일반적인 설정에서는 `origin/main` 같은 원격 추적 참조를 갱신하고, 현재 작업 브랜치에 자동으로 병합하지 않는다. `origin/main`은 원격 서버를 실시간으로 바라보는 창이 아니라 로컬에 기록된 관측값이다. [git-fetch](https://git-scm.com/docs/git-fetch)

`pull`은 가져오기 이후 통합까지 이어간다. 옵션과 설정에 따라 동작이 달라지므로 의도를 명시하는 편이 이해하기 쉽다. 예를 들어 `main`에서 `git pull --ff-only origin main`을 실행하면 fast-forward로 따라갈 수 있을 때만 갱신한다. 이력이 갈라졌다면 멈추고 별도의 판단을 요구한다. [git-pull](https://git-scm.com/docs/git-pull)

급한 일로 작업을 잠시 접어야 한다면 `git stash push -u -m "login 작업 중"`으로 미추적 파일까지 함께 보관할 수 있다. 무시된 파일은 `-u`의 대상이 아니다. 다시 적용하는 `git stash pop`도 충돌할 수 있으며, 충돌하면 해당 stash는 자동으로 삭제되지 않는다. [git-stash](https://git-scm.com/docs/git-stash)

<h2 id="branches">브랜치는 어떻게 갈라질까?</h2>

브랜치는 커밋을 가리키는 움직이는 이름이다. 브랜치를 만드는 데 프로젝트 전체 복사가 필요하지 않은 이유다. 보통 `HEAD`는 현재 브랜치를 가리키고, 새 커밋을 만들면 그 브랜치가 새 커밋을 가리킨다. 태그나 특정 커밋을 직접 체크아웃하면 HEAD가 커밋을 직접 가리키는 detached HEAD 상태가 될 수도 있다. [Git References](https://git-scm.com/book/en/v2/Git-Internals-Git-References)

아래 선은 부모 관계를 나타내며 시간은 왼쪽에서 오른쪽으로 흐른다.

```text
A──B──C       main
    └──D──E   feat/login-timeout ← HEAD
```

두 브랜치가 별도의 파일 묶음을 영구적으로 소유하는 것은 아니다. 같은 과거를 공유하다 서로 다른 커밋을 가리키고 있다. `switch`는 선택한 브랜치의 상태에 맞춰 작업 트리와 인덱스를 갱신한다. 덮어쓰일 미커밋 변경이 있으면 전환이 거부될 수 있으므로 먼저 상태를 확인한다. [브랜치 전환](https://git-scm.com/book/en/v2/Git-Branching-Basic-Branching-and-Merging)

내가 브랜치를 나누는 기준은 사람보다 변경의 목적이다. `sunjoon-work`에 여러 작업을 쌓으면 어디까지 리뷰하고 병합할지 불명확해진다. `feat/login-timeout`, `fix/session-expiry`처럼 목적을 좁혀 두면 끝나는 시점도 설명하기 쉽다.

<h2 id="integration">merge, rebase, squash의 선택</h2>

**merge**는 갈라진 이력을 연결한다. 아래에서 `main`에 기능 브랜치를 병합하면 M은 C와 E를 부모로 갖는다. 두 갈래에서 일했다는 사실이 남는다.

```text
A──B──C────M   main
    └──D──E┘   feat/login-timeout
```

대상 커밋이 현재 커밋의 후손이라면 브랜치 참조만 앞으로 옮기는 **fast-forward**도 가능하다. 이 경우 새 merge commit은 필요하지 않다. 일반적인 두 브랜치의 3-way merge는 공통 조상과 양쪽 상태를 비교한다. 단순히 최신 파일로 덮어쓰는 방식이 아니다. [병합의 원리](https://git-scm.com/book/en/v2/Git-Branching-Basic-Branching-and-Merging)

**rebase**는 내 커밋의 변경을 다른 기준점 위에 다시 적용한다. 앞의 D와 E를 C 위에 올리면 다음처럼 된다.

```text
A──B──C──D'──E'   feat/login-timeout
      ↑
     main
```

D와 E를 그대로 옮긴 것이 아니라 부모가 달라진 새 커밋을 만든다. 이력이 직선으로 읽히는 장점이 있지만, 커밋별로 충돌 해결이 반복될 수도 있다. 다른 사람이 기반으로 삼은 브랜치를 임의로 rebase하면 동료의 이력과 어긋난다. 나는 아직 공유하지 않은 작업을 정리할 때 우선 고려하고, 여러 사람이 쓰는 브랜치는 merge로 갱신하는 편을 기본으로 삼겠다. [git-rebase](https://git-scm.com/docs/git-rebase)

**squash**는 여러 커밋의 최종 변경을 한 커밋으로 정리하는 선택이다. `git merge --squash` 자체는 커밋을 만들지 않고, 결과를 준비한 뒤 별도로 커밋하게 한다. 이 커밋에는 기능 브랜치와의 부모 연결이 남지 않는다. [git-merge](https://git-scm.com/docs/git-merge)

따라서 선택 기준은 그래프의 모양만이 아니다. 개별 커밋이 각각 설명 가능한 작업이라면 이력을 보존할 가치가 있다. 수정과 재수정이 쌓였지만 PR 전체가 하나의 변경이라면 squash가 읽기 쉬울 수 있다. squash로 합친 브랜치는 작업을 마무리하고 최신 `main`에서 다음 브랜치를 시작하는 흐름을 권하고 싶다. 같은 브랜치를 계속 재사용하면 이미 반영한 변경의 이력까지 다시 비교해야 해 혼동하기 쉽다.

<h2 id="conflicts">충돌을 해결한다는 것</h2>

충돌은 Git이 망가졌다는 신호가 아니다. 자동으로 결정할 수 없는 선택이 남았다는 뜻이다. 겹치는 줄을 다르게 수정했거나 한쪽은 파일을 지우고 다른 쪽은 수정했을 때 등이 해당한다. 충돌 중 인덱스에는 경로별로 공통 조상과 양쪽 버전이 들어갈 수 있다. [git-merge](https://git-scm.com/docs/git-merge)

`feat/login-timeout`에서 `git merge origin/main`을 실행했다고 하자. 기능 브랜치는 재시도를 추가했고, `main`은 제한 시간을 설정값으로 바꿨다.

```js
<<<<<<< HEAD
const options = { timeout: 3000, retries: 2 };
=======
const options = { timeout: config.apiTimeout };
>>>>>>> origin/main
```

위나 아래를 통째로 고르면 한쪽의 의도가 사라진다. 두 요구를 모두 유지해야 한다면 해결 결과는 다음과 같을 수 있다.

```js
const options = { timeout: config.apiTimeout, retries: 2 };
```

물론 재시도와 제한 시간이 함께 작동해도 되는지는 사람이 확인해야 한다. 설정이 없을 때의 처리, 전체 대기 시간, 중복 요청 가능성까지 보는 것이 실제 해결이다. 자동 병합이 성공했더라도 이런 의미상의 충돌은 남을 수 있다.

내가 따르고 싶은 순서는 **양쪽의 의도 확인 → 최종 코드 작성 → 동작 검증 → 해결 상태 기록**이다. 아래 예제는 `src/api.js`에서 충돌했고 그 파일을 직접 편집했다고 가정한다.

```bash
git status
git diff --name-only --diff-filter=U
# 양쪽 변경을 읽고 src/api.js를 편집한다.
git diff --check
# 관련 테스트와 빌드를 실행한다.
git add src/api.js
git diff --staged
git merge --continue
```

`add`는 해결한 내용을 인덱스에 반영하는 단계다. 충돌 표시를 지웠다고 Git이 알아서 해결 완료로 취급하는 것은 아니다. `diff --check`도 공백 오류나 충돌 표시는 찾지만 프로그램의 정답을 판정하지는 않는다. 더 살펴봐야 한다면 `git merge --abort`로 병합을 중단할 수 있다. 시작 전에 작업을 커밋하거나 보관해 두어야 미커밋 변경의 복구 문제를 줄일 수 있다. [고급 병합](https://git-scm.com/book/en/v2/Git-Tools-Advanced-Merging), [diff 검사](https://git-scm.com/docs/git-diff)

rebase 중이라면 해결 후 `git add`와 `git rebase --continue`, 중단할 때는 `git rebase --abort`를 사용한다. 이때 `ours`는 새 기준점 위에 지금까지 재구성한 쪽, `theirs`는 재적용 중인 작업 쪽이다. 평소의 “ours는 내 코드”라는 감각으로 선택하지 말고 실제 내용을 확인해야 한다. [rebase의 충돌 처리](https://git-scm.com/docs/git-rebase)

<h2 id="teamwork">함께 일하기 위한 흐름</h2>

협업에서 시간을 줄이는 가장 좋은 지점은 충돌을 빨리 지우는 기술보다 **서로의 변경을 작고 일찍 이해하는 것**이라고 생각한다. 자주 통합하는 웹 서비스 팀이라면 다음처럼 시작할 수 있다. 명령을 실행하기 전 작업 트리가 깨끗한지 확인한다.

```bash
git switch main
git pull --ff-only origin main
git switch -c feat/login-timeout

# 구현하고 관련 테스트를 실행한다.
git add -p
git diff --staged
git commit -m "fix: 로그인 요청에 제한 시간 적용"
git push -u origin feat/login-timeout
```

이후 저장소 호스팅 서비스에서 `main`을 대상으로 PR을 연다. 설명에는 발생하던 문제, 바뀐 동작, 확인 방법을 적는다. “로그인 수정”보다 “응답이 끝나지 않으면 버튼이 계속 비활성화되던 문제를 고쳤고, 제한 시간 뒤 재시도가 가능한지 확인했다”가 리뷰어에게 유용하다.

리뷰 중 `main`이 바뀌었고 여러 사람이 이 기능 브랜치를 함께 사용한다면, 아래처럼 최신 변경을 병합한 뒤 통합 결과를 검증할 수 있다. 앞선 PR 예제의 기능 브랜치에서 실행하는 명령이다.

```bash
git fetch origin
git merge origin/main
# 충돌이 있으면 해결하고, 통합 결과의 테스트를 실행한다.
git push
```

브랜치 전략은 팀의 릴리스 방식에 맞춰야 한다. 나의 출발점은 짧게 유지하는 작업 브랜치와 안정적인 `main`이다. PR이 며칠씩 대기한다면 브랜치 이름 규칙보다 리뷰 대기 시간을 먼저 줄이겠다. 포맷 변경과 기능 변경도 나눠 리뷰 범위를 줄이겠다. 장기간 여러 배포 버전을 지원한다면 그때 유지보수 브랜치를 추가할 이유가 생긴다. Git 공식 워크플로 문서도 주제별 브랜치와 단계별 통합을 설명한다. [gitworkflows](https://git-scm.com/docs/gitworkflows)

`main`에는 리뷰와 필수 CI 검사를 적용하고, 팀이 선택한 병합 방식을 명시해 두는 구성을 제안한다. 미완성 기능은 작은 단위로 통합하되 기능 플래그 등으로 노출을 제어할 수 있다. 중요한 것은 누구나 “어떤 상태면 합쳐도 되는가”에 같은 답을 할 수 있는가다.

공유한 개인 브랜치를 합의하에 rebase했다면 원격 갱신에도 주의가 필요하다. `--force-with-lease`는 기대한 원격 상태와 다르면 덮어쓰기를 거부한다. 다만 인자 없이 쓰면 로컬 원격 추적 참조를 기준으로 삼기 때문에 백그라운드 fetch가 보호 의도를 약화할 수 있다. 이력 재작성을 합의하고 필요하면 명시적인 기대 커밋 ID를 사용하는 이유다. 강제 갱신을 일상적인 동기화 수단으로 삼지는 않겠다. [git-push의 lease 조건](https://git-scm.com/docs/git-push)

<h2 id="tags">태그로 남기는 릴리스의 기준점</h2>

브랜치가 다음 작업을 따라 움직인다면 태그는 특정 시점을 이름으로 남기는 데 쓴다. lightweight tag는 객체를 직접 가리키는 참조이고, annotated tag는 작성자·날짜·메시지 등을 담는 태그 객체를 가리킨다. 릴리스에는 설명을 남길 수 있는 annotated tag를 우선 고려하겠다. [git-tag](https://git-scm.com/docs/git-tag)

아래는 `main`의 최신 커밋이 실제 릴리스 승인 대상인지 확인한 뒤 태그를 만드는 예다. 별도 릴리스 브랜치를 쓴다면 그곳의 검증된 커밋을 선택해야 한다.

```bash
git switch main
git pull --ff-only origin main
git log -1 --oneline
# 이 HEAD가 CI를 통과한 릴리스 대상인지 확인한다.
git tag -a v1.4.0 -m "Release v1.4.0" HEAD
git show v1.4.0
git push origin v1.4.0
```

태그를 만들었다고 배포가 실행되는 것은 아니다. 태그 푸시를 배포 트리거로 쓰려면 CI/CD 설정이 별도로 필요하다. 모든 로컬 태그를 한꺼번에 보내기보다 릴리스할 태그를 지정해 푸시하면 대상을 확인하기 쉽다. [태그 푸시](https://git-scm.com/docs/git-push)

태그도 기술적으로는 변경할 수 있지만, 이미 공유한 릴리스 태그는 옮기지 않는 것을 팀의 약속으로 두고 싶다. 같은 `v1.4.0`이 사람마다 다른 코드를 뜻하면 장애를 추적할 기준이 무너진다. 수정이 필요하면 새 버전을 만든다. 또한 태그는 소스의 기준점일 뿐 실행 환경 전체를 저장하지 않으므로, 실제 배포 아티팩트와 설정의 식별 정보도 함께 남기는 편이 좋다.

<h2 id="recovery">실수한 뒤에 돌아오는 방법</h2>

되돌리기 전에 먼저 무엇을 되돌리려는지 구분한다. `git restore --staged src/api.js`는 스테이징만 취소하고 작업 파일은 남긴다. 반면 `git restore src/api.js`는 기본적으로 인덱스 내용으로 작업 파일을 덮어써 그 파일의 미스테이징 수정을 버린다. 비슷한 이름이어도 대상이 다르다. [git-restore](https://git-scm.com/docs/git-restore)

이미 팀에 공유한 잘못된 커밋에는 보통 `git revert`를 먼저 고려한다. 기존 이력을 지우지 않고 변경을 반대로 적용하는 새 커밋을 만든다. 아래는 커밋 ID를 실제 값으로 바꿔 실행하는 예이며, merge commit을 되돌릴 때는 별도로 부모 선택과 후속 병합에 대한 검토가 필요하다. [git-revert](https://git-scm.com/docs/git-revert)

```bash
git revert <잘못된-커밋-ID>
```

브랜치를 잘못 이동시켜 커밋이 보이지 않는다면 `git reflog`로 로컬 참조의 이동 기록을 찾을 수 있다. 원하는 커밋을 확인한 후 구조용 브랜치를 만들면 현재 작업을 곧바로 덮어쓰지 않고 내용을 살펴볼 수 있다.

```bash
git reflog
git branch rescue/login <찾아낸-커밋-ID>
```

reflog는 원격 팀 전체의 공용 기록이 아니며 만료될 수 있다. 커밋하지 않은 모든 편집 내용을 복구하는 장치도 아니다. 그래도 “커밋이 사라진 것 같다”는 순간에는 무작정 초기화하기보다 참조가 어디로 움직였는지부터 확인할 근거가 된다. [git-reflog](https://git-scm.com/docs/git-reflog)

<h2 id="reflection">내가 남기고 싶은 기록</h2>

Git을 들여다보면 일상의 명령어들이 다르게 읽힌다. `add`는 다음 스냅샷을 준비하고, `commit`은 그것을 이력에 연결한다. 브랜치는 작업의 위치를 가리키고, merge와 rebase는 그 이력을 서로 다른 방식으로 이어 붙인다.

그 위에서 좋은 협업을 만드는 것은 작은 선택들이다. 한 커밋에 이유 하나를 담고, 동료가 검토할 수 있을 때 변경을 공유하고, 충돌한 두 코드가 각각 무엇을 지키려 했는지 읽는 일. 릴리스에 이름을 붙이고, 잘못된 변경도 추적 가능한 방식으로 되돌리는 일이다.

내가 남기고 싶은 Git 이력은 몇 달 뒤의 동료가 “왜 이렇게 바뀌었지?”라고 물었을 때 답을 찾을 수 있는 기록이다. 다음 커밋에서 바로 해볼 수 있는 일도 크지 않다. `git diff --staged`를 한 번 더 읽고, 이 변경의 이유를 한 문장으로 써보는 것부터 시작하면 된다.
