<h2 id="beyond-features">기능 목록만으로 알 수 없는 차이</h2>

“이 저장소의 오류를 고쳐줘.” “다음에도 이 형식으로 보고서를 작성해줘.” “메신저에서 요청하면 내 서버에서 작업해줘.”

모두 AI 에이전트에 맡길 수 있는 일이지만, 각 작업에 필요한 구성은 다릅니다. 첫 번째에는 개발 도구와 실행 환경이, 두 번째에는 기억과 작업 지침이, 세 번째에는 연결과 지속적인 운영이 중요합니다.

에이전트를 고를 때 우리는 먼저 무엇을 할 수 있는지 살펴봅니다. 그런데 기능 목록만 나란히 놓으면 도구들은 비슷해 보입니다. 모델을 호출하고, 파일을 읽고, 명령을 실행하며, 외부 서비스와 연결하기 때문입니다. 차이는 이 기능들을 어떤 구조로 묶고, 사용자가 어느 범위까지 직접 설정하고 바꿀 수 있는지에 있습니다.

OpenClaw, Pi, Hermes Agent는 이 차이를 살펴보기 좋은 프로젝트입니다. 이 글에서 Pi는 **pi.dev의 에이전트 하네스**, Hermes는 **Nous Research의 Hermes Agent**를 가리킵니다. 공식 문서를 바탕으로 설계를 비교한 글이며, 직접 실행해 성능을 측정한 결과는 아닙니다. 문서 확인일은 2026년 11월 4일입니다.

<h2 id="pi">Pi: 내 작업 방식에 맞게 바꾸기</h2>

Pi를 이해하려면 먼저 **하네스**가 무엇인지 살펴볼 필요가 있습니다. 하네스는 모델이 도구를 사용하고 작업을 이어가도록 만드는 실행 환경입니다. 어떤 정보를 모델에 전달할지, 도구 호출을 어떻게 처리할지, 대화 이력을 어떻게 관리할지가 여기에 포함됩니다.

Pi는 핵심 기능을 작게 유지하면서 필요에 따라 확장할 수 있도록 설계했습니다. 확장 기능, 스킬, 프롬프트 템플릿, 테마를 조합해 작업 방식을 바꿀 수 있습니다. 터미널에서 직접 사용하는 것뿐 아니라 스크립트나 RPC로 제어하거나, TypeScript SDK로 다른 애플리케이션에 넣을 수도 있습니다. [Pi 공식 README](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/README.md)

이 철학은 기본 제공하지 않는 기능에서도 드러납니다. Pi는 서브에이전트나 계획 모드를 코어에 넣기보다 사용자가 확장하거나 패키지로 추가하도록 안내합니다. 작업 절차를 파일로 관리할지, 별도 UI로 만들지, 여러 에이전트에게 나누어 맡길지를 직접 결정하는 셈입니다. [Pi 공식 소개](https://pi.dev/)

예를 들어 팀 고유의 코드 검토 절차가 있다면, 그 절차에 맞춰 명령과 지침을 구성할 수 있습니다. 반면 원하는 기능이 기본 구성에 없다면 직접 추가하고 관리하는 노력도 필요합니다. Pi를 평가할 때는 기본 기능의 개수와 함께 **내 방식으로 바꾸는 데 드는 비용**을 살펴봐야 합니다.

<h2 id="openclaw">OpenClaw: 여러 채널과 기기에서 사용하기</h2>

OpenClaw에서는 **Gateway**가 중요한 역할을 맡습니다. 상시 실행되는 Gateway가 메신저 연결을 유지하고, CLI·웹 UI 같은 클라이언트와 여러 기기가 통신하도록 연결합니다. 여러 메신저와 기기에서 같은 에이전트 환경에 작업을 요청할 수 있는 구조입니다. [OpenClaw Gateway 아키텍처](https://docs.openclaw.ai/concepts/architecture)

이 구조에서는 비교할 항목도 달라집니다. 어떤 채널에서 들어온 요청인지, 어떤 세션으로 이어지는지, 어떤 기기와 도구를 사용할 수 있는지 확인하게 됩니다. 에이전트를 계속 켜두고 여러 곳에서 사용하려면 이런 요소들이 실제 사용 경험을 좌우합니다.

각 에이전트는 작업 디렉터리, 지침 파일, 세션 저장소를 가집니다. `AGENTS.md`, `SOUL.md`, `USER.md`, `MEMORY.md` 같은 파일은 작업 방식과 사용자 정보, 기억을 구성하는 데 사용됩니다. 따라서 OpenClaw를 단순히 메신저 연결 도구로 이해하면 부족합니다. **요청을 처리할 때 어떤 문맥과 규칙이 적용되는지**까지 함께 봐야 합니다. [OpenClaw 에이전트 런타임](https://docs.openclaw.ai/concepts/agent)

메신저와 기기를 오가며 에이전트를 지속적으로 사용하려는 사람이라면 이 운영 구조를 살펴볼 가치가 있습니다. 연결이 늘어날수록 설정하고 관리할 대상도 늘어납니다. 설치에 성공했는지에 더해, 재시작이나 연결 장애 후 작업을 어떻게 이어갈지도 평가해야 합니다.

<h2 id="hermes">Hermes: 경험을 다음 작업에 남기기</h2>

Hermes Agent는 기억과 스킬을 쌓아가는 기능을 주요 특징으로 내세웁니다. CLI, 데스크톱, 메신저를 지원하면서 이전 작업에서 얻은 정보와 절차를 이후 작업에 재사용하는 구조를 강조합니다. [Hermes 공식 문서](https://hermes-agent.nousresearch.com/docs)

여기서 ‘학습’의 의미를 구체적으로 볼 필요가 있습니다. 공식 문서에 따르면, 세션이 끝나도 유지되는 기본 기억은 `MEMORY.md`와 `USER.md`에 저장됩니다. 에이전트가 도구를 통해 내용을 추가하거나 수정하면, 다음 세션이 시작될 때 저장된 정보가 문맥에 들어갑니다. 과거 대화를 검색하는 기능도 따로 제공합니다. [Hermes 지속 기억](https://hermes-agent.nousresearch.com/docs/user-guide/features/memory)

스킬에는 재사용할 작업 지식을 담습니다. 사용자가 설명한 절차나 참고 자료를 바탕으로 스킬을 만들고, 필요한 작업에서 불러오는 방식입니다. Hermes가 말하는 성장의 핵심은 **이후 작업에 활용할 정보와 절차를 남기는 것**입니다. 이는 모델의 가중치를 다시 학습하는 과정과는 다릅니다. [Hermes 스킬 시스템](https://hermes-agent.nousresearch.com/docs/user-guide/features/skills)

예를 들어 보고서 작성 뒤 “결론을 먼저 쓰고, 수치에는 원문 링크를 붙여줘”라는 기준을 저장했다고 가정해 보겠습니다. 다음 세션에서도 그 기준을 실제로 사용하는지 확인해야 기억의 가치를 알 수 있습니다. 에이전트가 저장했다고 답하더라도 실제로 저장 도구를 호출했는지 확인해야 합니다. 공식 문서 역시 저장했다고 답하면서도 파일에는 기록하지 않는 경우를 설명합니다. [기억 저장 문제 해결](https://hermes-agent.nousresearch.com/docs/user-guide/features/memory)

기억이 저장되어 있다고 해서 항상 도움이 되는 것은 아닙니다. 필요한 것을 남기는지, 오래된 정보를 수정할 수 있는지, 비슷한 작업에서 적절한 절차를 불러오는지가 실제 효과를 결정합니다.

<h2 id="boundaries">서로 겹치는 기능과 달라지는 설계</h2>

Pi는 확장성, OpenClaw는 연결과 운영, Hermes는 기억과 재사용이라는 관점에서 살펴볼 수 있습니다. 다만 이는 각 프로젝트가 중요하게 다루는 부분을 정리한 해석입니다. OpenClaw에도 기억이 있고, Hermes에도 메시징 Gateway가 있으며, Pi도 확장을 통해 장기 기억을 구성할 수 있습니다. [OpenClaw 런타임](https://docs.openclaw.ai/concepts/agent), [Hermes 문서](https://hermes-agent.nousresearch.com/docs), [Pi 소개](https://pi.dev/)

빠르게 변하는 프로젝트에서는 과거의 설명이 현재 버전에도 맞는지 확인하는 것도 중요합니다. 예를 들어 Pi 공식 사이트는 MCP를 현재 기본 지원한다고 명시하고, 과거 입장을 바꾼 이유를 별도 글로 설명합니다. “Pi는 MCP를 지원하지 않는다”는 설명만으로는 현재 상태를 전달할 수 없습니다. [Pi의 MCP 도입 설명](https://earendil.com/posts/you-said-no-mcp/)

Pi와 OpenClaw의 관계를 설명할 때도 기준 시점을 밝혀야 합니다. Pi 문서는 OpenClaw를 통합 사례로 소개하지만, 현재 OpenClaw 문서는 OpenClaw가 직접 관리하는 통합 런타임을 설명합니다. 이 자료만으로 현재의 구체적인 의존 구조를 단정하기보다, 비교 대상 버전의 코드와 변경 이력을 확인하는 편이 정확합니다. [Pi README](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/README.md), [OpenClaw 런타임](https://docs.openclaw.ai/concepts/agent)

<h2 id="comparison">같은 작업으로 비교한다면</h2>

문서의 설계 방향을 기준으로 보면, 자신만의 작업 흐름을 구성하려는 개발자는 Pi를, 여러 채널과 기기에서 에이전트를 운영하려는 사용자는 OpenClaw를, 반복 작업에서 기억과 절차의 재사용을 중요하게 보는 사용자는 Hermes를 먼저 살펴볼 수 있습니다. 이는 먼저 살펴볼 도구를 고르는 기준이며, 성능 순위는 아닙니다.

실제 선택을 위해서는 같은 조건의 실험이 필요합니다. 동일한 모델과 유사한 도구 권한을 사용하고, 입력과 성공 기준을 맞춰야 하네스의 차이를 조금 더 분명히 볼 수 있습니다. 다음 그림은 실제 비교를 위해 제안하는 실험입니다.

메신저 예약 작업처럼 기본 구성의 차이가 큰 항목은 별도로 비교하는 편이 좋습니다. 기본으로 제공하지 않는 기능도 확장을 통해 구현할 수 있습니다. 구현할 수 있더라도 추가 설정과 유지보수 시간은 사용자가 부담하는 비용으로 기록해야 합니다.

세 프로젝트를 비교할 때는 **원하는 작업을 기본 기능만으로 처리할 수 있는지, 어떤 부분을 직접 구성해야 하는지** 살펴보면 좋겠습니다. 이 기준으로 사용해 보면 기능 목록만으로는 알기 어려웠던 차이가 드러납니다.
