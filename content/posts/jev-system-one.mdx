<h2 id="decisions">UI 문제라면, 바로 배정해도 될까?</h2>

버그 신고를 담당 팀에 보내는 기능을 만든다고 하자. 이런 신고가 들어왔다.

> 두 번째 창을 열면 저장 버튼이 사라집니다. 새로고침하면 다시 보입니다.

모델이 `ui`라고 답했다. 이제 UI 팀에 보내면 될까? 다른 분류보다 조금 더 그럴듯해서 골랐을 수도 있고, 확실하게 한쪽으로 판단했을 수도 있다. 선택값 하나만으로는 그 차이가 보이지 않는다.

이 글에서 살펴볼 **Jev**는 TypeSafe AI가 만든 모델이다. 회사는 소프트웨어가 바로 사용할 구조화된 판단에 초점을 둔 모델 계열을 **System One**이라고 부른다. Jev의 입출력을 따라가면서, 모델의 판단을 코드의 처리 규칙으로 바꾸는 경계를 살펴보자. [공식 소개](https://docs.typesafe.ai/introduction)

<h2 id="system-one">Jev가 돌려주는 것은 무엇인가</h2>

Jev에 보내는 핵심 재료는 두 가지다. **`state`는 판단할 자료**, **`questions`는 그 자료에 관해 묻는 질문**이다. 버그 신고 원문을 주고 어떤 분류에 해당하는지, 재현 정보가 얼마나 구체적인지 등을 묻는다.

돌아오는 것은 자유롭게 작성한 설명문이 아니라 선택값·점수·확률이다. 코드는 이 값을 받아 배정하거나, 보류하거나, 추가 정보를 요청할 수 있다. [입출력과 질문 구성](https://docs.typesafe.ai/introduction)

```text
신고 원문 + 판단 기준
          ↓
   Jev: 분류와 확률
          ↓
   코드: 배정 규칙 적용
          ↓
   담당 팀 또는 검토 대기열
```

생성 모델에도 구조화된 출력을 요청할 수 있다. Jev를 검토할 이유는 JSON을 만들 수 있다는 사실만으로 설명되지 않는다. TypeSafe는 구조화된 판단에 집중한 설계와 속도·비용을 차별점으로 제시한다. 그 주장이 내 서비스에서도 유효한지는 같은 입력과 기준으로 비교해야 한다. [공식 발표](https://typesafe.ai/blog/introducing-system-one-models-and-jev)

여기서는 API를 호출하지 않았다. 아래 문장과 수치는 동작을 이해하기 위한 가상 예시이며, 실제 성능이나 한국어 분류 정확도를 보여주는 결과가 아니다.

<h2 id="primitives">한 신고에 묻는 세 가지 질문</h2>

“이 신고를 알아서 처리해줘”를 조금 더 작은 질문으로 나눠보자. 분류, 재현 정보, 임시 해결 방법은 서로 다른 판단이다.

[Choice](https://docs.typesafe.ai/primitives/choice)는 순서가 없는 선택지 중 하나를 고른다. UI는 화면 표시·조작 문제, API는 요청·응답 문제가 명시된 경우로 기준을 적을 수 있다. 이 목록에 맞지 않는 신고를 위해 ‘기타’도 둔다. 이 분류는 원인 진단이 아니라 **신고에 서술된 증상**을 기준으로 한다.

[Score](https://docs.typesafe.ai/primitives/score)는 순서가 있는 기준을 먼저 작성한다. 이 글에서는 0을 ‘증상만 있음’, 1을 ‘재현 행동 또는 실행 환경 중 하나가 있음’, 2를 ‘둘 다 있음’으로 정해보겠다. 앞의 신고에는 행동은 있지만 브라우저·앱 버전 같은 환경 정보가 없다. 이처럼 무엇을 보고 단계를 구분할지 적어야 점수를 읽을 수 있다.

[Noul](https://docs.typesafe.ai/primitives/noul)은 예·아니오로 답할 질문에 쓴다. “임시 해결 방법이 적혀 있는가?”라면 ‘새로고침하면 다시 보인다’는 문장이 판단 재료다. 반환값이 0.8이라면 ‘예’일 확률을 나타낸다. 해결 방법의 품질이 80점이라는 뜻은 아니다.

세 질문을 한 요청에 함께 넣을 수 있지만, 각 질문은 같은 입력에 대해 독립적으로 평가된다. 두 번째 질문이 첫 번째 답을 읽는 구조는 아니다. **답 사이의 조건과 조합은 코드에서 처리한다.** [독립된 질문과 코드에서의 조합](https://docs.typesafe.ai/introduction)

<h2 id="composition">같은 UI라도 다른 처리</h2>

이제 Choice 하나에 집중해보자. 아래의 첫 두 사례는 모두 `ui`를 선택하지만 확률 분포가 다르다. ‘두 분류가 비슷’을 선택한 뒤 최고 확률 하한을 0.80에서 0.50으로 내려보자. **모델의 선택값을 바꾸지 않아도 코드의 처리 결과는 바뀐다.**

<JevDecision />

이 예제에서는 최고 확률이 기준 이상이면 해당 팀에 배정하고, 기준보다 낮거나 ‘기타’이면 검토 대기열에 보낸다. 그림에서 바꾼 것은 모델의 능력이 아니라 **그 출력을 받아들이는 정책**이다. 하한은 설명용 값이며, 낮출수록 정확도가 어떻게 변하는지는 실제 신고로 측정해야 한다.

시각 자료의 배정 규칙을 코드로 옮기면 다음과 같다. API 호출과 응답 검증을 마친 뒤 사용하는 함수이며, 네트워크 오류 처리는 생략했다.

```js
function route(probabilities, threshold = 0.8) {
  const ranked = Object.entries(probabilities)
    .sort((a, b) => b[1] - a[1]);
  const [choice, probability] = ranked[0];

  if (choice === "other" || probability < threshold) {
    return "review";
  }
  return choice;
}

route({ ui: 0.86, api: 0.10, other: 0.04 }); // "ui"
route({ ui: 0.51, api: 0.47, other: 0.02 }); // "review"
```

분류값만 저장했다면 두 결과가 모두 UI였다는 사실만 남는다. 분포와 적용한 기준을 함께 남기면 왜 한 건은 자동 배정되고 다른 건은 보류됐는지 추적할 수 있다.

<h2 id="confidence">확률, 점수, confidence를 구분하기</h2>

비슷한 숫자로 보여도 쓰임은 다르다. 앞의 시각 자료에서 배정 기준으로 사용한 값은 <strong>선택된 항목의 확률</strong>이다. 화면에 함께 표시한 `confidence`는 별도의 값이다.

Choice의 `confidence`는 가장 높은 확률이 균등 분포보다 얼마나 높은지를 나타낸다. 공식 문서의 계산식은 다음과 같다. `n`은 선택지 수, `p_max`는 최고 확률이다. [Confidence의 정의와 계산식](https://docs.typesafe.ai/confidence)

```text
confidence = (p_max − 1/n) ÷ (1 − 1/n)

선택지 3개, 최고 확률 0.86
→ (0.86 − 1/3) ÷ (1 − 1/3) = 0.79
```

따라서 첫 사례의 확률 0.86과 confidence 0.79는 서로 바꿔 쓸 수 없다. 이 confidence가 실제 정답률 79%를 보장하지도 않는다. 최고 확률이 같으면 나머지 확률이 어떻게 나뉘었든 Choice confidence는 같다. 자세한 경계를 보고 싶다면 분포도 함께 읽어야 한다.

Score의 점수는 또 다르다. **단계 번호에 각 확률을 곱한 뒤 더한 값**이다. 앞서 정한 재현 정보의 세 단계에 가상의 확률을 넣어보자. [Score 결과 해석](https://docs.typesafe.ai/primitives/score)

```text
단계       0     1     2
확률     0.1   0.3   0.6

score = 0×0.1 + 1×0.3 + 2×0.6 = 1.5
```

1.5는 작성한 기준 위의 점수다. ‘정답률 75%’로 읽으면 안 된다. 기준을 심각도로 바꾸면 같은 숫자도 다른 의미를 갖는다. Noul에는 별도 `confidence` 필드가 없으며, ‘예’일 확률 자체를 읽는다.

<h2 id="evaluation">자동화할 경계는 직접 검증한다</h2>

TypeSafe가 강조하는 타입 안전성은 정해진 스키마에 맞는 값을 반환한다는 보장이다. `ui`라는 유효한 값을 반환하면서도 실제 분류는 틀릴 수 있다. **출력 형식이 맞는지와 판단이 맞는지는 각각 확인해야 한다.** [발표문의 타입 안전성 설명](https://typesafe.ai/blog/introducing-system-one-models-and-jev)

이 기능을 실제로 만든다면 먼저 사람이 분류한 한국어 신고를 준비하겠다. 명확한 사례, UI와 API의 경계, 정보가 부족한 사례, 기타에 해당하는 사례를 포함한다. 기준을 조정하는 데이터와 마지막 평가에 쓸 데이터도 나눈다.

확인할 수치는 두 가지를 함께 둔다. **자동 배정한 신고 중 맞게 배정한 비율**, 그리고 **전체 신고 중 자동 배정한 비율**이다. 전자만 높고 대부분의 신고를 사람이 다시 본다면 자동화의 효과는 작다. 반대로 자동 배정만 늘리면 잘못 보낸 신고를 되돌리는 일이 많아질 수 있다.

기존 규칙이나 구조화 출력을 쓰는 모델과 같은 신고로 비교하고, 실제 배포 환경의 지연과 재시도를 포함한 비용도 잰다. API 호출 실패는 낮은 확률의 정상 응답과 구분해 처리한다.

Jev를 보며 흥미로웠던 것은 판단을 작은 질문으로 나누고, 그 답을 사용하는 기준을 코드로 드러내는 방식이다. “UI로 분류됐다”에서 멈추지 않고, <strong>“어떤 분포였고, 어떤 규칙으로 배정했는가?”</strong>까지 설명할 수 있어야 한다.
