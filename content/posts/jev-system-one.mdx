<h2 id="decisions">소프트웨어가 필요한 것은 작은 판단일 때가 많다</h2>

버그 신고를 분류하는 기능을 만든다고 하자. 사용자가 남긴 글을 읽고 UI 문제인지, API 문제인지, 문서 오류인지 골라야 한다. 재현 절차가 충분한지도 확인하고 싶다. 이 단계에서 필요한 결과는 긴 답변보다 분류값 몇 개다.

규칙으로 처리할 수 있는 부분도 있다. 첨부 파일의 유무와 앱 버전은 코드로 확인하면 된다. 하지만 “두 번째 창을 열면 저장 버튼이 사라져요” 같은 문장의 의미를 해석하는 일은 조건문만으로 다루기 번거롭다.

TypeSafe AI는 2026년 9월 15일 이런 판단을 겨냥한 첫 공개 모델 **Jev**를 얼리 액세스로 발표했다. 회사는 이 모델 계열을 **System One**이라고 부른다. 자연어로 주어진 상태를 읽고, 소프트웨어가 사용할 수 있는 구조화된 판단을 반환한다는 접근이다. [공식 발표](https://typesafe.ai/blog/introducing-system-one-models-and-jev)

내가 흥미롭게 보는 지점은 모델을 호출한 다음이다. 결과를 어떻게 해석하고, 언제 자동으로 처리하며, 어떤 사례를 남겨둘 것인가? Jev의 인터페이스를 보면 이 질문이 애플리케이션 설계의 중심으로 올라온다.

<h2 id="system-one">TypeSafe가 말하는 System One</h2>

Jev는 입력 상태인 `state`와 질문인 `questions`를 받아 정해진 타입의 답을 돌려준다. 자유로운 문장이나 코드를 생성하는 인터페이스는 제공하지 않는다. 여기서 System One은 TypeSafe가 붙인 모델 계열의 이름이며, 사람의 인지 과정을 그대로 구현했다는 의미로 받아들일 필요는 없다. [System One 개념](https://docs.typesafe.ai/concepts/system-one)

회사는 새로운 모델 아키텍처, 병렬 샘플러, **RLCD(Reinforcement Learning for Calibrated Decisions)**라는 학습 방식을 소개한다. 다만 이 글에서 확인한 발표 자료만으로 내부 구현을 재현하거나 다른 아키텍처와 동일한 조건으로 비교하기는 어렵다. 먼저 공개된 입출력 계약과 평가 결과를 살펴보는 편이 실용적이다. [공식 발표](https://typesafe.ai/blog/introducing-system-one-models-and-jev)

생성 모델도 구조화된 분류 결과를 반환하도록 사용할 수 있다. 실제로 TypeSafe의 비교 평가도 다른 모델을 호환되는 구조화 출력으로 감싼다. 따라서 비교할 지점은 JSON을 반환할 수 있는지 자체보다, **같은 판단을 어떤 품질·지연·비용으로 수행하는지**다. [공식 발표의 비교 방식](https://typesafe.ai/blog/introducing-system-one-models-and-jev)

현재 모델 문서에는 `jev-1.13.0`이 명시되어 있다. 텍스트 입력을 지원하며, 영어에서 정확도가 가장 높다고 설명한다. 한국어 서비스에 적용한다면 한국어 데이터로 별도 평가해야 한다. [모델 문서](https://docs.typesafe.ai/models)

<h2 id="primitives">Choice, Score, Noul을 구분하기</h2>

세 타입의 차이는 반환 형식보다 **무엇을 묻고 있는가**에 있다.

      <tr><td>Noul</td><td>임시 해결 방법이 언급되어 있는가?</td><td>그 명제가 참일 확률</td></tr>

**Choice**는 미리 정의한 선택지 중 하나를 고른다. 가장 높은 확률의 항목인 `choice`, 선택지별 `probabilities`, 분포를 요약하는 `confidence`를 반환한다. UI와 API 중 하나를 무조건 고르게 만들면 둘 다 아닌 신고도 그 안에 들어간다. 예시에서는 `other`를 두고, 이 분류에 모인 신고를 검토하는 편을 택하겠다. [Choice 문서](https://docs.typesafe.ai/primitives/choice)

**Score**는 순서가 있는 기준에 대한 평가다. 예를 들어 0은 “재현 행동이 없음”, 1은 “행동은 있으나 필요한 조건이 빠짐”, 2는 “환경과 행동 순서가 구체적으로 제시됨”으로 정의할 수 있다. 반환 점수는 단계 번호를 확률로 가중한 평균이다. 가상의 분포가 `[0.1, 0.3, 0.6]`이라면 점수는 `0×0.1 + 1×0.3 + 2×0.6 = 1.5`다. **1.5점은 정답률 75%를 뜻하지 않는다.** [Score 문서](https://docs.typesafe.ai/primitives/score)

**Noul**은 예·아니오 질문에 대해 ‘예’일 확률을 0~1로 반환한다. 임시 해결 방법의 존재 여부에 대한 값이 0.8이라면, 그것을 해결 방법의 품질이 80점이라고 읽으면 안 된다. Noul에는 별도 `confidence` 필드가 없다. [Noul 문서](https://docs.typesafe.ai/primitives/noul)

같은 신고를 보더라도 분류, 재현 절차의 구체성, 해결 방법의 존재 여부는 서로 다른 판단이다. 한 점수로 압축하기 전에 각각 어떤 결정을 위해 필요한지부터 정해야 한다.

<h2 id="composition">판단을 나누고, 코드에서 조합한다</h2>

아래는 버그 신고를 분류하는 요청 본문 예시다. 공식 HTTP API의 `POST /v1/systemone` 형식에 맞췄지만, 실제 호출 결과를 포함한 튜토리얼은 아니다. [API 레퍼런스](https://docs.typesafe.ai/api)

```json
{
  "model": "jev-1.13.0",
  "state": {
    "report": "두 번째 창을 열면 저장 버튼이 사라집니다. 새로고침하면 다시 보입니다."
  },
  "questions": {
    "category": {
      "type": "choice",
      "instructions": "신고에 직접 서술된 증상의 주된 분류를 고르세요. 원인을 추측하지 마세요.",
      "criteria": {
        "ui": "화면 표시나 화면 조작의 문제",
        "api": "API 요청 또는 응답의 문제가 명시됨",
        "docs": "설명서의 오류 또는 누락",
        "other": "위 분류에 해당하지 않거나 분류할 정보가 부족함"
      }
    },
    "has_workaround": {
      "type": "noul",
      "instructions": "신고자가 증상을 일시적으로 해소하는 방법을 명시했나요?"
    }
  }
}
```

질문의 이름인 `category`만 보고 모델이 의도를 추론한다고 기대하면 안 된다. API 문서에 따르면 질문 ID는 모델에 전달되지 않는다. 판단에 필요한 의미는 `instructions`와 `criteria`에 작성해야 한다. [API 레퍼런스](https://docs.typesafe.ai/api)

한 요청 안의 질문들은 같은 상태를 대상으로 각각 독립적으로 평가된다. 따라서 두 번째 질문에 “첫 번째 답이 UI라면…”이라고 적는 방식은 질문 간 의존성을 구현하지 못한다. 먼저 필요한 판단을 함께 받은 뒤 코드에서 분기하거나, 앞선 결과가 꼭 필요하면 다음 호출의 입력에 넣어야 한다. [소개 문서](https://docs.typesafe.ai/introduction)

아래 관계도는 이 글에서 제안하는 역할 분담이다. 선은 연결 관계를 나타내며, 실행 순서를 표시하는 화살표가 아니다. 항목을 선택하면 각 역할의 설명을 읽을 수 있다.

이 설계에서 모델은 신고의 의미를 판단하고, 코드는 그 결과를 어느 대기열에 넣을지 결정한다. 버전 비교나 신고 횟수 계산은 코드에 남긴다. 분류가 애매한 사례는 검토 대상으로 보내고, 사용자에게 설명문이 필요하면 별도의 생성 단계에서 근거를 제공한다.

<h2 id="confidence">확률과 confidence를 읽는 법</h2>

Choice의 확률 분포가 가령 UI 0.51, API 0.47, 나머지 0.02라면 `choice`는 UI다. 하지만 선택된 항목만 저장하면 API와 거의 비슷했다는 정보가 사라진다. 자동 분류 정책을 만들 때는 선택값과 함께 분포를 남겨두는 편이 유용하다.

공식 문서에서 `confidence`는 Choice와 Score의 확률 분포가 얼마나 집중되거나 퍼져 있는지를 요약한 값이다. **`confidence: 0.9`를 해당 답이 맞을 확률 90%로 바로 해석해서는 안 된다.** 문서의 정의만으로 최대 확률이나 특정 엔트로피 공식과 같다고 가정할 수도 없다. [Confidence 문서](https://docs.typesafe.ai/confidence)

확률이 잘 보정되었다는 주장도 여러 사례를 모아 검증해야 한다. 예를 들어 ‘예’일 확률이 0.8 부근인 신고 100개를 모았을 때 실제로 약 80개가 조건을 만족하는지 확인하는 방식이다. 이 예시는 보정의 의미를 설명하기 위한 것이며, Jev에서 측정한 결과가 아니다.

실험에서는 자동 처리할 비율과 오분류를 함께 보겠다. 임계값을 높여 자동 처리한 신고의 정확도가 좋아지더라도, 대부분을 사람이 검토해야 한다면 얻는 효과가 작을 수 있다. 반대로 자동 처리율만 높이면 잘못 배정된 신고를 되돌리는 비용이 늘어난다.

여기에 타입 안전성도 구분해야 한다. TypeSafe가 발표에서 강조하는 보장은 스키마 일치다. **정해진 선택지만 반환하는 것과 올바른 선택지를 고르는 것은 별개의 성질**이다. API가 UI라는 유효한 값을 반환해도 실제 분류가 틀릴 수 있다. [공식 발표의 타입 안전성 설명](https://typesafe.ai/blog/introducing-system-one-models-and-jev)

실제로 회사의 Jev 1.13 한계 문서에는 수치 계산, 날짜 비교, 복잡한 간접 추론, 무관한 정보가 많은 입력, 적대적 입력에 대한 취약점이 명시되어 있다. 타입이 정해져 있다는 이유로 의미적 오류나 프롬프트 인젝션까지 해결되었다고 볼 수 없다. [Jev 1.13의 알려진 한계](https://docs.typesafe.ai/model-jaggedness/jev-1.13)

<h2 id="evidence">빠르고 저렴하다는 주장은 어디까지 확인됐을까?</h2>

확인일 기준 가격은 입력 100만 토큰당 **0.042달러**, 출력 토큰은 무료다. 문서상 입력 한도는 요청 전체 64k 토큰이며, 별도로 `state`와 가장 긴 질문을 합한 길이는 32k 이내여야 한다. [모델과 가격 문서](https://docs.typesafe.ai/models)

이 단가로 입력 1,000토큰인 요청을 100만 번 처리한다고 단순 계산하면 모델 입력 요금은 42달러다. 이는 필자의 산술 예시다. 실제 청구 입력량, 재시도, 다른 모델 호출, 저장과 운영 비용을 포함한 견적은 아니다.

발표문은 종단 간 응답 시간 70~500ms를 제시하지만, 측정이 서비스가 위치한 미국 서부 인근에서 주로 이루어졌다고 설명한다. 한국의 실제 서비스에서 같은 지연을 얻는다는 보장으로 읽기는 어렵다. [공식 발표의 측정 조건](https://typesafe.ai/blog/introducing-system-one-models-and-jev)

공개 평가 사이트는 보안 사고, 에이전트 실행 기록, 송장 처리, 고객 서비스의 네 워크플로를 비교한다. 주목할 점은 기준 답안이다. 사람이 확정한 정답 대신 대형 모델 응답의 평균을 기준으로 삼고, 워크플로 코드가 올바르다고 가정한다. 그래프의 각 점은 네 작업에 같은 가중치를 준 평균이다. [Workflow evals](https://evals.typesafe.ai/)

내 해석은 이렇다. 이 결과는 공개된 작업 구성에서 속도·비용과 기준 모델에 대한 일치도를 살펴보는 자료다. 한국어 버그 신고의 정확도나 실제 운영 성과를 직접 입증하지는 않는다. 비교 실험에서는 같은 입력과 기준을 사용하고, 분류 결과만 필요한 기존 모델에 불필요하게 긴 설명을 생성시키지 않아야 한다.

<h2 id="rag">RAG에 넣는다면 어디에 둘까?</h2>

[이전 RAG 글](/posts/rag-beyond-similarity)에서는 검색 결과의 순위와 근거의 충분함을 구분했다. Jev를 그 구성에 넣는다면, 나는 우선 **검색된 문서 조각을 평가하는 구간**에서 실험하겠다.

공식 cookbook에도 검색한 각 문서에 대해 관련성, 답변 근거의 유무, 질문의 전제와 충돌하는 내용, 모델을 조종하려는 지시 등을 나누어 묻는 예제가 있다. 코드는 결과에 따라 근거와 충돌 자료를 구분하거나 후보에서 제외한다. 해당 예제는 `jev-1.12`로 기록되었으므로 현재 버전의 재측정 결과와 혼동하지 않아야 한다. [RAG 문서 분류 예제](https://docs.typesafe.ai/cookbooks/classifying_rag_passages)

```text
질문 → 후보 검색 → 문서별 판단 → 코드에서 근거 선택 → 답변 생성
                     │
                     ├─ 질문과 관련이 있는가?
                     ├─ 답변에 쓸 근거가 있는가?
                     └─ 질문의 전제와 충돌하는가?
```

이 구성의 가치는 판단을 나누어 관찰할 수 있다는 데 있다. 단일 관련성 점수로는 놓치기 쉬운 차이를 별도의 질문으로 정의할 수 있다. 대신 그 질문이 실제 실패를 줄이는지, 추가 지연과 비용에 비해 효과가 있는지 확인해야 한다.

또한 후보에 들어오지 않은 근거를 이 단계가 복구해주지는 않는다. 자료를 지나치게 걸러내면 답변에 필요한 문서를 잃을 수도 있다. 기존 검색·리랭킹 구성과 비교할 때는 최종 답변 품질과 함께 **필요한 근거를 얼마나 보존했는지**를 측정하겠다.

<h2 id="evaluation">첫 실험에서 확인할 것</h2>

처음부터 자동 실행 범위를 넓히기보다는, 기존 처리 결과와 나란히 비교할 수 있는 버그 분류부터 시작하겠다. 다음은 이 글의 설계 제안이다.

1. **평가할 신고를 고른다.** 명확한 사례뿐 아니라 UI와 API의 경계, 정보 부족, 복합 증상, 한국어 구어체를 포함한다. 사람이 판단하기 어려운 사례도 따로 표시한다.
2. **정책과 질문을 분리한다.** 분류 기준을 문장으로 작성하고, 점수에 따른 배정 규칙은 코드에서 관리한다. 기준을 다듬는 데이터와 마지막 평가 데이터는 분리한다.
3. **같은 조건에서 비교한다.** 기존 규칙, 구조화 출력을 쓰는 기존 모델, Jev를 같은 신고로 평가한다. 자동 분류 정확도와 자동 처리율을 함께 기록한다.
4. **운영 전체를 잰다.** 실제 배포 지역에서 p50·p95 지연, 오류와 재시도, 후속 모델 호출까지 포함한 비용을 확인한다. API 오류를 낮은 확률과 같은 상태로 취급하지 않는다.
5. **변경을 추적한다.** 모델 버전, 질문과 기준의 버전, 결과 분포, 사람이 수정한 라벨을 남긴다. 모델이나 기준이 바뀌면 같은 평가 세트로 다시 비교한다.

`jev-latest`는 새 릴리스에 따라 가리키는 모델이 바뀐다. 임계값을 검증한 실험에서는 버전 ID를 고정하고 응답의 실제 모델 ID도 기록하는 편이 재현에 유리하다. [모델 별칭과 버전](https://docs.typesafe.ai/models)

Jev를 통해 살펴볼 만한 변화는 AI의 판단을 더 작은 단위로 설계하는 방식이다. 무엇을 모델에 묻고, 어떤 근거를 주며, 그 답을 어느 조건에서 사용할지 명시해야 한다. 이 경계가 분명할수록 틀린 결과를 추적하고 다음 실험을 설계하기도 쉬워진다.
