<h2 id="deployment-and-users">새 버전이 떴는데, 왜 기다릴까?</h2>

새 컨테이너 두 개가 실행됐다. 상태는 `RUNNING`. 이제 기존 버전을 꺼도 될까?

프로세스가 실행된 것과 사용자 요청을 처리할 준비가 된 것은 다르다. 설정을 읽거나 연결을 준비하는 중일 수 있다. 이때 기존 버전을 먼저 끄면, 서버는 떠 있는데 요청은 실패하는 순간이 생긴다.

**배포는 새 버전을 켜는 일과 기존 버전을 끄는 일 사이의 순서를 설계하는 작업**이다. 이 글에서는 HTTP API 하나를 v1에서 v2로 바꾸며, 그 사이에도 요청이 이어지는 조건을 살펴본다.

등장하는 AWS 서비스는 역할로 기억하면 된다. **ECS**는 태스크의 실행과 교체를 관리한다. 태스크는 여기서 API 컨테이너 하나를 실행하는 단위다. **Fargate**는 그 컨테이너를 실행할 서버를 직접 관리하는 부담을 줄여준다. **ALB**는 사용자 요청을 받아 대상 태스크에 전달하고 준비 상태를 검사한다. [Fargate와 로드 밸런싱](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/AWS_Fargate.html)

<h2 id="rolling-deployment">다섯 장면으로 보는 버전 교체</h2>

v1 태스크 두 개가 정상적으로 요청을 처리하고 있다고 하자. v2는 실행된 뒤 준비 상태 검사를 통과해야 새 요청을 받는다. 예제 앱의 `/health/ready`는 초기화 중에는 503, 준비가 끝나면 200을 반환하도록 만든다. ALB의 성공 응답 코드는 200으로 설정한다.

아래에서 **03 준비 통과 → 04 v1 제외**를 눌러보자. v1의 역할이 ‘새 요청 수신’에서 ‘기존 요청 마무리’로 바뀐다. 03에서 **준비 검사 실패**로 전환하면, 같은 시점에 v2로 요청을 보내지 못하는 이유를 볼 수 있다.

이 그림은 두 태스크를 함께 교체하는 한 가지 흐름을 단순화한 것이다. 실제 ECS는 준비 속도와 설정에 따라 하나씩 교체할 수도 있다. 자동 확장과 배포 조기 성공 옵션은 예제에서 제외했다.

읽어야 할 차이는 **실행 수, 새 요청을 받을 수 있는 수, 진행 중인 요청**이다. 세 가지가 같은 순간에 바뀌지는 않는다. ALB는 정상 대상을 확인해 요청을 전달한다. 다만 모든 대상이 비정상이면 비정상 대상에도 요청을 보내는 fail-open 예외가 있으므로, 그림은 정상 v1이 남아 있다는 전제에서 읽어야 한다. [ALB 대상 상태와 fail-open](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/target-group-health-checks.html)

<h2 id="what-to-change">태스크 두 개를 네 개로 늘리는 이유</h2>

평소에는 두 개면 충분한데, 왜 배포 중에는 네 개가 필요할까? **기존 버전이 일하는 동안 새 버전을 준비할 공간**을 확보하기 위해서다.

ECS의 롤링 배포에서는 `minimumHealthyPercent`가 유지할 정상 태스크의 하한을, `maximumPercent`가 실행·시작 대기 중 태스크의 상한을 정한다. `desiredCount`가 2일 때 아래 설정은 정상 태스크 하한 2개와 실행·대기 상한 4개를 만든다. [배포 설정의 의미](https://docs.aws.amazon.com/AmazonECS/latest/APIReference/API_DeploymentConfiguration.html)

```json
{
  "desiredCount": 2,
  "deploymentController": { "type": "ECS" },
  "deploymentConfiguration": {
    "strategy": "ROLLING",
    "minimumHealthyPercent": 100,
    "maximumPercent": 200,
    "deploymentCircuitBreaker": {
      "enable": true,
      "rollback": true
    }
  }
}
```

이것은 서비스 설정의 일부다. 태스크 정의, 네트워크, 권한, 대상 그룹을 따로 연결해야 한다. 위 JSON만으로 실행 환경이 만들어지지는 않는다.

```text
정상 태스크 하한 = 올림(2 × 100 / 100) = 2
실행·대기 상한   = 내림(2 × 200 / 100) = 4
```

상한 4는 네 개를 반드시 동시에 띄우라는 명령이 아니다. 자원과 할당량이 허용할 때 기존 두 개를 남기고 새 두 개를 시작할 수 있다는 뜻이다. 또한 하한 설정은 장애가 생겨도 언제나 두 개가 정상이라는 가용성 보장이 아니다.

ALB를 쓰는 이 구성에서는 단순히 `RUNNING`이 된 것만으로 정상 수에 포함되지 않는다. 대상 그룹의 헬스 체크를 통과해야 하며, 필수 컨테이너의 헬스 체크도 설정했다면 그 결과까지 확인한다. 그래서 그림의 두 번째 장면은 ‘실행 네 개, 새 요청 대상 두 개’다.

<h2 id="application">기존 요청은 어디에서 끝날까?</h2>

v2가 준비됐다. 이제 v1을 대상에서 빼면 될까? v1에서 10초 걸리는 파일 처리가 이미 시작됐을 수도 있다. 새 요청을 보내지 않는 것과 이미 받은 요청을 끊는 것은 다른 일이다.

ALB의 <strong>드레이닝(draining)</strong>은 대상을 제외하면서 진행 중인 요청을 마무리할 시간을 주는 과정이다. 애플리케이션도 종료 신호를 받으면 진행 중 작업을 정리할 수 있어야 한다. 기다리는 시간은 요청 길이와 종료 처리에 맞춰야 한다. [연결 드레이닝과 종료 처리](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/load-balancer-connection-draining.html)

```text
v1에서 시작한 요청 ────────────── 완료
                 ↑                ↑
            새 요청 대상 제외   종료 가능

새로 들어온 요청 ──→ 준비된 v2에서 처리
```

그림의 04 단계에서 v1은 이 마지막 일을 하고 있다. 태스크가 화면에서 사라졌는지보다 **그 태스크가 받은 요청이 끝났는지**를 봐야 한다. 긴 업로드나 스트리밍이 있다면 짧은 HTTP 요청과 같은 종료 정책을 그대로 적용하기 어렵다.

두 버전이 동시에 살아 있는 동안에는 데이터도 함께 읽는다. 예를 들어 v1이 사용하는 DB 컬럼을 v2 배포와 동시에 삭제하면, 태스크가 정상이어도 v1의 요청은 실패한다. 새 필드를 추가하고 두 버전이 함께 사용할 기간을 둔 뒤 옛 필드를 제거하는 식으로 호환성을 준비해야 한다. 이미지 롤백이 삭제한 데이터를 복구해주지는 않는다.

<h2 id="failed-deployment">준비에 실패한 버전은 어떻게 될까?</h2>

이번에는 v2의 준비 경로가 계속 503을 반환한다고 하자. 시각 자료를 **준비 검사 실패**로 바꾸면 v1은 계속 요청을 받고, v2는 끝내 새 요청 대상이 되지 않는다.

위 설정의 배포 서킷 브레이커는 태스크가 실행되지 못하거나 헬스 체크 실패가 누적되는 상황을 감지해 배포 실패를 판정한다. 롤백을 켰다면 마지막으로 완료된 배포로 돌아간다. **돌아갈 `COMPLETED` 배포가 있어야 한다.** 첫 배포에도 똑같이 복구할 수 있다고 가정하면 안 된다. [서킷 브레이커와 롤백](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/deployment-circuit-breaker.html)

실패 검사 한 번이 곧 롤백은 아니다. 실패 기준에 도달하고 복구가 끝나기까지 시간이 걸린다. 그림의 03 ‘준비 실패’와 04 ‘실패 판정’을 나눈 이유다. 실제 확인에는 ECS 서비스 이벤트와 `rolloutState`, `rolloutStateReason`을 함께 본다.

하지만 `/health/ready`만 200이고 실제 저장 API는 500을 반환한다면 어떨까? 이 경우 v2는 요청을 받을 수 있다. 준비 검사만으로 기능 오류까지 잡을 수는 없다. 주요 API의 성공 여부와 오류율을 관찰하고, 필요한 CloudWatch 경보를 배포 실패 감지에 연결하는 방법을 검토한다. [경보를 통한 배포 실패 감지](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/deployment-alarm-failure.html)

<h2 id="next-step">배포 성공을 무엇으로 확인할까?</h2>

내가 이 구성을 시험한다면 배포 버튼을 누르기 전부터 요청을 기록하겠다. 버전, 요청 ID, 시작·완료 시각, 응답 코드가 있으면 태스크의 교체와 사용자가 겪은 결과를 연결할 수 있다.

첫 검증은 세 장면이면 된다. 아래는 실제 측정 결과가 아닌, 실험 전에 정할 관찰 항목이다.

오류가 없었다는 관찰에는 표본 수와 트래픽 조건도 붙여야 한다. 드문 요청으로 짧은 장애를 놓칠 수 있고, 두 태스크가 감당하지 못하는 부하에서는 다른 결과가 나올 수 있다. 태스크 수만으로 요청의 성공을 증명할 수는 없다.

무중단 배포를 이해하는 기준은 ‘새 버전이 실행됐다’에서 한 걸음 더 나아간다. **준비된 곳으로 새 요청을 보내고, 이미 받은 요청을 끝내며, 실패한 변경에서 돌아올 수 있는가.** 그 세 가지를 설명할 수 있을 때 배포 설정의 숫자에도 이유가 생긴다.

<h2 id="references">참고 자료</h2>

2026년 10월 17일 AWS 공식 문서를 확인했다. 본문의 API, 시각 자료와 실험은 설명용 설계이며 실제 AWS 배포 결과가 아니다.

- [ECS와 Fargate](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/AWS_Fargate.html): 실행 환경과 로드 밸런싱.
- [DeploymentConfiguration](https://docs.aws.amazon.com/AmazonECS/latest/APIReference/API_DeploymentConfiguration.html): 롤링 배포의 태스크 수와 정상 판정 조건.
- [ALB 헬스 체크](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/target-group-health-checks.html): 대상 상태와 fail-open 예외.
- [연결 드레이닝](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/load-balancer-connection-draining.html): 진행 중 요청과 종료 처리.
- [배포 서킷 브레이커](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/deployment-circuit-breaker.html): 실패 판정과 롤백 조건.
- [CloudWatch 배포 경보](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/deployment-alarm-failure.html): 준비 검사 밖의 실패를 관찰하는 방법.
