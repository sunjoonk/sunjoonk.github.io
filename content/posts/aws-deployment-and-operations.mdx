<h2 id="deployment-and-users">배포를 사용자 경험에서 바라보기</h2>

서비스의 배포와 운영을 공부하면서 자주 돌아오게 되는 질문이 있다. 새 버전을 배포하는 동안에도 사용자는 하던 일을 계속할 수 있을까?

개발자에게 배포는 변경한 코드를 서비스에 반영하는 과정이다. 사용자에게는 그 과정 자체보다 요청이 정상적으로 처리되고, 작성하던 내용과 진행 중인 작업이 이어지는지가 중요하다. 짧은 요청 실패도 사용자에게는 처음부터 다시 해야 하는 일이 될 수 있다.

그래서 무중단 배포를 특정 도구의 기능 하나보다, **새 버전의 준비를 확인하고 요청을 넘긴 뒤 문제가 생기면 복구하는 일련의 과정**으로 이해하고 싶다. 실행 환경과 애플리케이션, 데이터가 함께 준비돼야 가능한 일이다.

이 글에서는 **가상의 웹 API를 v1에서 v2로 배포하는 과정**을 따라간다. 먼저 ECS와 Fargate를 선택할 조건을 살펴보고, 정상 배포와 실패 배포에서 요청이 어디로 가는지 확인한다. 마지막에는 독자가 작은 검증 환경에서 재현할 실험과 판정 기준을 정리한다. 구성과 수치는 학습용 예시이며 실제 서비스의 운영 구성이나 실험 결과를 나타내지 않는다.

<h2 id="what-to-change">안정적인 배포에 필요한 순서</h2>

배포 자동화는 빠뜨리는 절차를 줄이고 배포 이력을 남기는 데 도움이 된다. 여기에 요청의 연속성을 확보하려면, 버전이 교체되는 순서와 각 단계의 성공 조건도 설계해야 한다.

무중단 배포의 기본 흐름을 다음과 같이 정리해봤다.

1. 기존 버전이 요청을 처리하는 동안 새 버전을 실행한다.
2. 새 버전이 요청을 받을 준비가 됐는지 확인한다.
3. 준비된 새 버전으로 요청을 보내고, 기존 버전이 처리하던 요청을 마무리한다.
4. 문제가 생기면 배포를 중단하고 검증된 이전 버전으로 돌아간다.

각 단계에서 무엇을 확인하고 언제 다음 단계로 넘어갈지 명확해야 한다. 배포 시점도 상태를 관찰하고 문제가 생겼을 때 대응할 수 있는 여건을 고려해 정해야 한다.

이 글에서 무중단 배포의 목표는 **버전 교체 때문에 사용 중인 요청이 실패하지 않도록 하는 것**이다. 서버 장애나 데이터베이스 장애까지 모두 해결했다는 뜻은 아니다. 배포 중 요청의 연속성과 서비스 전체의 가용성을 구분해서 설계해야 한다.

<h2 id="why-aws">AWS에서는 무엇을 맡길 수 있을까?</h2>

무중단 배포를 구현하는 방법은 여러 가지다. 여기서는 컨테이너 교체와 상태 확인, 실패 감지를 지원하는 AWS의 관리형 서비스를 살펴보려 한다. 각 기능을 연결했을 때 배포 절차가 어떻게 만들어지는지가 관심의 중심이다.

관리형 서비스를 사용하더라도 **배포의 성공 기준과 실패했을 때의 대응**은 직접 정의해야 한다. 도구에 맡길 실행 절차와 애플리케이션의 특성에 따라 결정할 부분을 나누어 이해하면 도움이 된다.

이 예제에서 사용할 조합은 **Amazon ECR, Amazon ECS, AWS Fargate, Application Load Balancer**다. 이름이 많아 처음에는 복잡하지만, 각각에 맡길 역할로 나누면 이해하기 쉽다.

ECR은 이미지 레지스트리다. ECS의 태스크 정의는 이미지, CPU·메모리, 실행 설정 등을 기술하고, 태스크는 그 정의로 실행되는 단위다. 하나의 태스크에는 여러 컨테이너가 들어갈 수도 있다. ECS 서비스는 지정한 수의 태스크를 유지한다. Fargate를 사용하면 컨테이너 실행용 EC2 서버를 직접 관리하지 않아도 되지만, 애플리케이션의 자원 크기와 네트워크, IAM 권한은 여전히 설계해야 한다. [ECR 개요](https://docs.aws.amazon.com/AmazonECR/latest/userguide/what-is-ecr.html), [ECS와 Fargate](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/AWS_Fargate.html)

학습용 배포 구성을 단순하게 그리면 다음과 같다.

```text
코드 변경 → CI에서 테스트·이미지 빌드 → ECR에 보관
                                          ↓
                              새 태스크 정의로 ECS 배포

사용자 → ALB → Fargate에서 실행되는 ECS 태스크
                 ├─ 기존 버전: 요청 처리
                 └─ 새 버전: 준비·상태 확인 후 요청 처리
```

ALB는 ECS 서비스의 여러 태스크로 HTTP/HTTPS 요청을 분산할 수 있다. 로드 밸런서와 네트워크의 접근 범위는 서비스의 공개 여부와 접근 요구사항에 맞게 설계해야 한다. [ECS의 로드 밸런싱](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/service-load-balancing.html)

<h3>이 구성이 적합한 조건과 부담스러운 조건</h3>

이 글의 예제는 컨테이너로 실행할 수 있는 HTTP API이며, 두 개 이상의 복제본이 같은 요청을 처리할 수 있다고 가정한다. 로그인 세션이나 파일처럼 유지할 상태는 태스크 바깥에서 관리하고, v1과 v2가 잠시 함께 동작할 수 있다. 이런 조건에서 ECS 서비스의 교체 기능과 ALB의 요청 분산을 연결해볼 이유가 생긴다.

Fargate가 줄여주는 범위는 컨테이너 실행용 서버의 프로비저닝과 관리다. 태스크 자원·네트워크·권한 구성은 남고, 지원하지 않는 태스크 설정도 있다. 따라서 선택의 기준은 **줄어드는 서버 관리 업무가 새로 익힐 설정과 비용을 감수할 만큼 의미 있는가**다. [Fargate의 관리 범위와 제약](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/AWS_Fargate.html)

<h2 id="rolling-deployment">새 버전이 준비된 뒤에 넘겨주기</h2>

가상의 `sample-api`는 태스크 하나에 API 컨테이너 하나를 실행한다. 응답에 `version`을 포함하는 `GET /version`과, 초기화 전에는 503을 반환하고 준비가 끝나면 200을 반환하는 `GET /health/ready`가 있다고 가정한다. v1과 v2의 기능은 같고 응답의 버전 값만 다르다. 여기서는 데이터 변경 없이 컨테이너 교체부터 관찰한다.

ECS에서 **태스크 정의는 실행 설정의 버전**, **태스크는 그 설정으로 실행한 인스턴스**, **서비스는 원하는 태스크 수와 배포를 관리하는 단위**다. 이 예제에서는 v1 이미지를 지정한 태스크 정의에서 v2 이미지를 지정한 새 리비전으로 서비스를 업데이트한다.

<h3>어떤 설정을 어디에 넣는가</h3>

아래 JSON은 ECS 서비스 설정 중 배포 관련 필드만 발췌한 것이다. 전체 서비스를 생성하는 파일은 아니며, 로드 밸런서·네트워크·태스크 정의는 별도로 연결해야 한다.

```json
{
  "desiredCount": 2,
  "deploymentController": { "type": "ECS" },
  "deploymentConfiguration": {
    "strategy": "ROLLING",
    "minimumHealthyPercent": 100,
    "maximumPercent": 200,
    "deploymentCircuitBreaker": { "enable": true, "rollback": true }
  },
  "healthCheckGracePeriodSeconds": 60
}
```

롤링 전략인 `ROLLING`을 사용한다. `desiredCount`가 2일 때 최소 정상 비율 100%는 배포 중 정상 태스크 하한 2개, 최대 비율 200%는 실행 중이거나 준비 중인 태스크 상한 4개를 뜻한다. 새 버전을 시작할 여유를 주는 설정이며, 자원·할당량도 이를 수용해야 한다. 자동 확장과 배포 조기 성공 옵션은 이번 예제에서 사용하지 않는다. [ECS 배포 설정](https://docs.aws.amazon.com/AmazonECS/latest/APIReference/API_DeploymentConfiguration.html)

`healthCheckGracePeriodSeconds=60`은 시작 직후의 실패한 헬스 체크를 ECS 스케줄러가 일정 시간 무시하도록 주는 유예다. **60초 동안 ALB가 무조건 기다리거나, 준비되지 않은 태스크에 요청을 보내도 된다는 의미는 아니다.** ALB의 요청 전달 여부는 대상의 상태 확인으로 결정된다. [ECS 서비스 설정](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/service_definition_parameters.html)

대상 그룹은 ALB가 요청을 보낼 태스크들을 묶어 관리하는 단위다. Fargate 예제에서는 대상 유형을 `ip`로 두고, 헬스 체크 경로를 `/health/ready`, 성공 코드를 `200`으로 설정한다. 학습용으로 검사 간격 10초, 타임아웃 5초, 정상·비정상 임계값 각각 2회를 사용한다. 이 수치는 시작 시간과 실패 감지 속도를 관찰하기 위한 출발점이다. 신규 대상의 초기 정상 판정은 한 번의 성공으로 가능하므로 모든 전환이 정확히 20초 뒤에 일어난다고 계산해서는 안 된다. [Fargate의 로드 밸런싱](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/AWS_Fargate.html), [ALB 헬스 체크 설정](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/target-group-health-checks.html)

<h3>v1 두 개에서 v2 두 개로 바뀌는 과정</h3>

아래는 정상 배포에서 가능한 흐름이다. 새 태스크 두 개가 모두 정상으로 판정된 뒤 기존 태스크를 제거하는 모습을 단순화했다. 실제로는 준비 속도에 따라 하나씩 교체될 수 있으며, 이 설정이 정확한 교체 순서를 고정하지는 않는다.

      <tr><th scope="row">1. 배포 전</th><td>v1 A·B가 정상</td><td>응답은 v1이다. 배포 전 오류율과 응답 시간을 기록한다.</td></tr>

      <tr><th scope="row">3. 새 버전 준비 완료</th><td>v2가 헬스 체크를 통과해 healthy가 됨</td><td>ALB가 v2에도 요청을 보낸다. 이때 v1·v2 응답이 섞여도 정상이다.</td></tr>
      <tr><th scope="row">4. 기존 버전 제외</th><td>v1 대상이 draining 상태로 전환</td><td>기존 요청을 마무리한다. 진행 중 요청의 성공 여부와 종료 로그를 확인한다.</td></tr>
      <tr><th scope="row">5. 교체 완료</th><td>v2 두 개가 남고 v1은 종료</td><td>새 요청에서 v2를 확인하고 ECS 배포 완료와 사용자 요청 결과를 함께 확인한다.</td></tr>
    </tbody>
  </table>
</div>

롤링 배포에서는 **새 태스크가 요청을 받기 시작하는 시점이 배포 전체의 완료보다 빠를 수 있다.** v1과 v2가 섞이는 구간이 있으므로 응답 형식과 데이터의 호환성이 필요하다. 태스크 수가 유지돼도 각 태스크가 감당할 처리량이 부족하면 오류가 생길 수 있다. [ECS 롤링 배포](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/deployment-type-ecs.html)

태스크가 `RUNNING`이라는 사실도 준비 완료와 같지 않다. 필수 컨테이너의 헬스 체크까지 설정했다면 ECS는 해당 검사와 로드 밸런서 검사의 정상 판정을 모두 기다려 정상 태스크 수에 포함한다. 준비 상태 경로는 실제 초기화 조건을 반영하되, 모든 외부 의존성의 일시 장애를 즉시 컨테이너 교체로 이어지게 만들지는 않아야 한다. [배포 시 정상 상태 판정](https://docs.aws.amazon.com/AmazonECS/latest/APIReference/API_DeploymentConfiguration.html)

<h2 id="failed-deployment">새 버전이 실패하면 어디로 돌아갈까?</h2>

이번에는 v1 배포가 `COMPLETED`인 상태에서, 준비 상태 경로가 계속 503을 반환하는 `v2-broken`을 배포한다고 가정한다. 기존 v1은 정상이고 두 태스크만으로 테스트 트래픽을 처리할 수 있다.

```text
v1 A·B 정상 → v2-broken 시작 → 준비 상태 검사 실패
     │                             ↓
     │                     실패 누적·배포 실패 판정
     │                             ↓
     └─ 요청 처리 유지 ← 마지막 완료 배포 v1로 롤백
```

새 태스크가 정상으로 판정되지 않는 동안에는 정상 v1이 요청을 처리한다. 서킷 브레이커가 실행 실패나 헬스 체크 실패를 기준으로 배포 실패를 판정하면, 롤백 옵션에 따라 마지막 `COMPLETED` 배포로 돌아간다. 돌아갈 완료 배포가 없는 첫 배포에서는 같은 복구를 기대할 수 없다. [배포 서킷 브레이커와 롤백 조건](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/deployment-circuit-breaker.html)

롤백은 새 버전의 첫 오류와 동시에 완료되는 동작이 아니다. 시작 시간, 검사 간격, 유예 시간과 실패 임계값에 따라 감지까지 시간이 걸린다. 실패한 배포의 `rolloutState`와 `rolloutStateReason`, 서비스 이벤트를 보고 실패 판정과 복구 진행을 구분해야 한다. 이미 교체가 일부 진행됐다면 이전 버전의 태스크를 다시 시작해야 할 수도 있다. [실패 판정과 배포 상태](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/deployment-circuit-breaker.html)

이 시나리오는 **정상 v1 대상이 남아 있다는 조건**에 의존한다. ALB는 대상 그룹에 비정상 대상만 남으면 그 대상들로도 요청을 보내는 fail-open 동작을 한다. 따라서 “헬스 체크가 실패한 버전은 어떤 상황에서도 사용자에게 노출되지 않는다”라고 일반화하면 안 된다. [ALB의 상태 확인과 fail-open](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/target-group-health-checks.html)

또 하나의 실패는 준비 상태 검사는 통과하지만 실제 API만 500을 반환하는 경우다. 이때는 새 버전에도 요청이 갈 수 있고 서킷 브레이커만으로 기능 오류를 감지할 수 없다. 주요 API 검증과 오류율 관찰을 추가하고, CloudWatch 경보를 배포 실패 감지와 롤백에 연결할지 결정해야 한다. [CloudWatch 경보를 통한 배포 실패 감지](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/deployment-alarm-failure.html)

<h2 id="application">컨테이너 바깥과 안쪽에 남는 문제</h2>

앞의 흐름이 사용자 요청의 성공으로 이어지려면 애플리케이션도 준비돼 있어야 한다. 특히 종료 처리, 상태 저장 위치, 데이터 호환성이 배포 설정과 맞아야 한다.

<h3>기존 요청을 끝내고 종료하기</h3>

새 태스크로 요청을 보내기 시작해도 기존 태스크에는 처리 중인 요청이 남아 있을 수 있다. 로드 밸런서의 연결 드레이닝은 대상을 빼는 동안 진행 중인 요청이 마무리될 시간을 주는 과정이다. 애플리케이션도 종료 신호를 받으면 새 작업 수신을 멈추고 진행 중인 작업을 정리하는 graceful shutdown을 지원해야 한다. [연결 드레이닝과 종료 신호](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/load-balancer-connection-draining.html)

이때 연결을 기다리는 시간과 컨테이너의 종료 대기 시간은 실제 요청 길이를 기준으로 맞춰야 한다. 긴 업로드나 스트리밍이 있다면 짧은 API 요청과 같은 설정으로 다루기 어렵다. 오래 유지되는 연결은 재연결했을 때 작업을 이어가는 방식까지 검토해야 한다.

<h3>어느 컨테이너로 가도 이어지는 상태 만들기</h3>

먼저 확인할 것은 로그인 세션, 업로드 파일, 백그라운드 작업이 어디에 남는지다. 세션이 특정 프로세스 메모리에만 있다면 다른 태스크가 요청을 받았을 때 로그인 상태를 이어받지 못할 수 있다. 파일이 컨테이너의 임시 저장 공간에만 있다면 교체 뒤에도 보존된다고 가정할 수 없다.

설계 단계에서 상태를 목록으로 정리하고, 여러 태스크가 공유하거나 영속적으로 보관할 위치를 정해야 한다. 여러 태스크에서 같은 예약 작업이 중복 실행되지 않는지도 확인할 항목이다. 컨테이너 수를 늘리는 일이 애플리케이션에는 새로운 동시성 조건이 될 수 있다.

<h3>이전 버전도 읽을 수 있는 데이터 유지하기</h3>

롤링 배포 중에는 이전 코드와 새 코드가 같은 데이터베이스를 사용할 수 있다. 새 코드에 맞춰 컬럼부터 삭제하거나 이름을 바꾸면, 아직 요청을 처리하는 이전 코드가 실패할 수 있다. 이 경우 이미지만 되돌린다고 문제가 해결되지 않는다.

예를 들어 이름을 저장하는 필드를 바꾼다면, 새 필드를 추가하고 필요한 기간 동안 두 필드를 함께 읽거나 쓰는 코드를 먼저 배포한다. 기존 데이터를 이관하고 이전 버전으로 돌아갈 필요가 없어진 뒤 옛 필드를 제거한다. 마이그레이션은 별도 단계에서 실행해 중복 실행과 실패를 통제한다.

**되돌릴 수 있는 배포를 만들려면 이미지뿐 아니라 데이터의 호환성도 남겨둬야 한다.**

<h2 id="operations">배포가 끝난 뒤에도 서비스는 계속된다</h2>

배포 명령이 성공했다고 운영이 끝나지는 않는다. 새 버전이 실제 요청을 잘 처리하는지 확인해야 한다. 배포할 이미지와 커밋, 배포 시각을 연결해 기록하는 것도 중요한 설계 항목이다. `latest`라는 이름만 보고 추측하지 않도록 커밋별 태그를 덮어쓰지 않게 관리하고, 배포한 이미지의 digest도 기록한다.

CI에서 한 번 빌드한 이미지를 검증하고 그 동일한 이미지를 배포한다. 이렇게 하면 검증한 산출물과 실제 실행하는 산출물을 일치시킬 수 있다. 이전 이미지와 태스크 정의도 보관해야 복구에 사용할 수 있다.

관찰 위치를 미리 정해두면 배포가 멈췄을 때 어디서부터 확인할지 분명해진다.

로드 밸런서가 생성한 5xx와 애플리케이션 대상이 반환한 5xx는 원인이 다를 수 있다. ALB 지표만으로 클라이언트의 모든 연결 오류가 집계되는 것은 아니므로, 실험에서는 요청을 보내는 쪽의 결과도 함께 기록한다. [ALB CloudWatch 지표](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/load-balancer-cloudwatch-metrics.html)

ECS에서는 `awslogs` 로그 드라이버를 설정해 컨테이너의 표준 출력과 표준 오류를 CloudWatch Logs로 보낼 수 있다. 로그가 모이는 것에 더해, 어느 상황에서 알림을 받고 무엇을 확인할지도 정해야 한다. [ECS 로그를 CloudWatch로 보내기](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/using_awslogs.html)

비용도 운영의 일부다. Fargate의 실행 자원 비용 외에 로드 밸런서, 이미지와 로그 보관, 데이터베이스, 데이터 전송, 네트워크 구성에 따른 NAT Gateway나 VPC 엔드포인트 비용도 계산에 포함한다. 월 비용은 리전과 자원 크기, 트래픽을 정한 뒤 계산해야 한다. 평상시 태스크 2개의 비용과 배포 중 추가되는 태스크의 실행 시간을 구분해 견적을 낸다. [Fargate 요금과 추가 비용 안내](https://aws.amazon.com/fargate/pricing/)

서버를 직접 관리하는 일이 줄어드는 만큼, 권한과 비밀값, 네트워크 접근, 백업과 복구를 이해해야 한다. AWS를 공부하며 중요하게 느끼는 것은 지원받을 부분을 정하고, 직접 판단해야 할 운영의 책임을 분명히 이해하는 일이다.

<h2 id="next-step">작게 검증하고, 실패도 연습하기</h2>

첫 실험은 세션이나 데이터 변경이 없는 `sample-api`로 범위를 좁힌다. `/version`은 `{"version":"v1"}` 같은 JSON을 반환하게 하고, 초기화 완료를 지연시키거나 준비 상태 검사를 실패시키는 설정을 예제 앱에 둔다. 이 설정은 실험용 애플리케이션에 직접 구현해야 하며 AWS가 자동으로 제공하는 기능은 아니다.

<h3>실험을 시작하기 위한 준비</h3>

1. v1, 정상 v2, 준비 상태가 계속 실패하는 v2-broken 이미지를 ECR에 보관하고 각각을 참조하는 태스크 정의 리비전을 만든다.
2. VPC·서브넷·보안 그룹을 구성한다. ALB에서 태스크의 API 포트로 접근할 수 있어야 하고, 태스크는 이미지와 로그 서비스에 접근할 네트워크 경로와 필요한 실행 역할 권한을 가져야 한다.
3. ALB 리스너를 `ip` 유형 대상 그룹에 연결하고 준비 상태 경로를 설정한다. ECS 서비스에는 이 대상 그룹과 컨테이너 이름·포트를 연결한다.
4. 앞의 서비스 설정으로 v1 태스크 두 개를 실행한다. 두 대상이 정상이고 v1 배포가 `COMPLETED`인지 확인한 뒤 요청을 보내기 시작한다.

설정 과정은 [Fargate Linux 태스크 시작 가이드](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/getting-started-fargate.html)와 [ECS에 ALB 연결하기](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/alb.html)를 참고할 수 있다. 이 글의 설정 발췌만으로 네트워크와 서비스가 생성되지는 않는다.

<h3>배포 중에도 요청을 계속 보내기</h3>

다음 명령은 읽기 전용 `/version` 경로에 순차적으로 요청을 보내고 시각, HTTP 상태, 소요 시간과 버전을 남긴다. `BASE_URL`을 직접 만든 검증 환경의 접근 가능한 주소로 바꾼다. 한 터미널에서 실행하고, 다른 화면에서 ECS 서비스의 태스크 정의를 v2 리비전으로 업데이트한다.

```bash
BASE_URL="https://your-test-api.example.com"

while true; do
  printf '%s ' "$(date -u '+%Y-%m-%dT%H:%M:%SZ')"
  curl --silent --show-error --connect-timeout 2 --max-time 5 \
    --write-out ' status=%{http_code} total=%{time_total}s\n' \
    "$BASE_URL/version"
  sleep 1
done
```

Ctrl+C로 종료한다. 연결 오류는 오류 메시지와 상태 코드도 함께 확인한다. 이 루프는 응답 시간에 1초를 더한 간격으로 실행되므로 고정 초당 요청 수나 부하 시험을 의미하지 않는다. 드문 요청 사이의 짧은 장애를 놓칠 수 있고, 정상 결과만으로 운영 트래픽에서의 무중단을 증명할 수는 없다.

<h3>네 가지 실험과 판정 기준</h3>

각 실험 전에 v1이 다시 정상 배포된 상태인지 확인한다. 정상 배포 1분 전부터 교체 또는 복구 완료 1분 후까지 요청 결과를 기록한다. 아래는 실측 결과가 아닌 **실험 전에 정해둘 예시 기준**이다.

처리 중 종료 실험은 별도의 10초짜리 경로를 구현하고 요청 제한 시간을 20초 이상으로 늘려 수행한다. 예를 들어 대상 그룹의 등록 해제 지연을 30초, 태스크 정의 내 컨테이너의 `stopTimeout`을 30초로 두고, 앱이 종료 신호를 받으면 진행 중 요청을 마친 뒤 종료하게 한다. 위 `/version` 루프의 5초 제한으로 긴 요청을 검사하면 클라이언트가 먼저 끊으므로 별도 요청이 필요하다. [연결 드레이닝](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/load-balancer-connection-draining.html), [Fargate 태스크 정의와 stopTimeout](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/task_definition_parameters.html)

배포 시작 전에 긴 요청을 한 번만 보내면 태스크 교체 전에 요청이 끝나버릴 수 있다. 버전·태스크 식별자·요청 ID를 로그에 남기고, v1 요청의 시작과 완료 사이에 해당 대상의 제외가 실제로 일어났는지 확인한다. 겹친 요청이 없다면 종료 처리를 검증한 것으로 판정하지 않고 실험 시점을 조정한다.

복구 시간은 예를 들어 5분 이내라는 학습용 목표를 먼저 정하고 측정한다. 이 값은 AWS의 보장이 아니다. 초과했다면 시작 지연, 유예 시간, 실패 판정과 롤백 실행 중 어디서 시간이 걸렸는지 분해해서 살펴본다. 응답 지연도 배포 전후 p95를 비교할 수 있지만, 표본 수와 요청량을 함께 기록해야 의미가 있다.

기본 실험 뒤에는 준비 상태 검사만 통과하고 실제 API는 500을 반환하는 버전을 추가해보면 좋다. 이 실험의 확인 대상은 자동 롤백 자체가 아니라 **현재의 검사로 놓치는 실패가 무엇인지**다. 이후 API 검사나 CloudWatch 배포 경보를 연결하고 감지·복구 실험을 반복한다.

<h2 id="reflection">사용자의 흐름을 이어주는 배포</h2>

AWS의 배포 기능을 공부할수록 서비스에 대한 이해가 먼저 필요하다는 생각이 든다. 새 버전이 정상이라고 판단할 기준, 요청을 마무리하는 데 필요한 시간, 두 버전이 함께 사용할 데이터의 형태를 알아야 설정에도 이유가 생긴다.

ECS와 Fargate는 그 판단을 실행하는 데 도움을 줄 수 있다. 여기에 상태 확인과 롤백, 로그와 알림을 연결하고 실제 실패 상황에서 검증해야 운영할 수 있는 배포 절차가 된다.

내가 공부하며 확인하고 싶은 기준은 분명하다. **새 버전이 배포되는 동안에도 사용자가 하던 일을 이어갈 수 있는가.** 작은 환경에서 그 과정을 관찰하고, 실패와 복구까지 설명할 수 있도록 이해를 쌓아가려 한다.
